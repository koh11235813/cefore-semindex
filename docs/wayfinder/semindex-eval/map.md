# Semantic Index 計測（段 1：切断率による基準計測）

## Destination

直線 5 ノードの ReCefore 上で、Semantic Index の pull 同期を、リンクの切断率を変えて繰り返し走らせる。発見までの時間、全ノードが一致するまでの時間、probe の発見率、制御の通信量を、条件ごとに 100 個以上の seed で測る。あわせて、エージェントが判断した瞬間の状態と行動を記録し、index の状態制御に RL のような学習制御を使えるかを検討するための材料にする。

この effort が出すのは、研究室への報告に使える正確な数字と、段 2（RL 向けのデータ収集）の設計を決めるための根拠まで。性能の優位を示すことや、RL の制御器を作ることは目的に含めない。

## Notes

- 実行（execution）型の effort。計測の道具を作り、run を回し、集計まで行う。
- 前提は `docs/wayfinder/semantic-index/` の初期ベースライン（チケット 01〜08 が closed）。プロトコルと名前の形式、時間とサイズの既定値は、その map の決定をそのまま使う。
- 用語は `CONTEXT.md`、構造的な決定は `docs/adr/`。
- 対象外: RL の制御器の実装と学習、段 2 の計測そのもの、トポロジーを変える計測（木や格子）、切断の周期を変える計測、本体（ファイル）を put する publisher を複数にすること。

## Decisions so far

### 目的と段の分け方（2026-10-23 決定）
- 目的は二つ。研究室への報告と、index の状態制御に RL のような学習制御を使えるかの検討。だから数字は正確であること、データは多いことを優先する。
- 計測を二段に分ける。切断率の効き目と制御の値の効き目を、同じデータの中で混ぜないため。
  - **段 1（この effort）**: 制御の値は既定値に固定し、切断率だけを変える。
  - **段 2（別の effort）**: エージェントが判断するたびに、行動を確率で選ぶ（探索のある行動方針）。オフラインの RL と off-policy 評価の元データにする。中身は段 1 の結果を見てから決める。いまはデータが無いので、どの値を制御させるかも決めない。

### トポロジーと負荷
- 直線 5 ノード h0–h1–h2–h3–h4。全ホストでエージェントを動かす。`links` は明示し、`k: 1`。
- Index origin は両端の h0 と h4。それぞれ 2 秒に 1 件、合計 30 件を作る。本体を put する publisher は h0 の 1 台だけ（生成器の制約）。h4 のレコードの `content_name` は本体の無い名前になる。
- レコードの属性（`zone`・`disaster`・`media`）は、seed から各語彙の一様分布で引く。本体の URI は固定。
- probe は真ん中の h2 から 10 秒ごとに出す。条件の `zone` も seed から一様に引く。
- run の長さは、生成が終わってから 60 秒の余裕を取って、およそ 120 秒。

### 切断の起こし方
- 変える軸は切断率 p だけ。p は 0・0.1・0.2・0.3・0.4 の 5 段階。
- リンクごとに、5 秒の区切りごとに確率 p で「落とす」かを決める。落ちている時間の割合の期待値が p になる。周期は 5 秒で固定する（状態確認の周期 2 秒より長く、run の長さより十分短い）。
- ReCefore には、リンクの切断を seed の乱数で決める仕組みが無い（周期的な `repeat` だけがある）。だから生成器が seed から切断の予定を引き、`link_down` と `link_up` のイベントを並べて出す。引いた予定は生成した YAML にそのまま残るので、あとから見直せる。

### 反復
- 条件ごとに seed 100 個（5 条件で 500 回）。切断なしの 5 ノードで、1 回は片づけを含めて 150 秒だった（2026-10-23、チケット 01）。500 回でおよそ 21 時間。切断のある条件で長くなるかは、チケット 04 の試走で確かめる。
- Mininet は 1 台のマシンで一度に 1 つしか走らせられない（`mn -c` が全体を片づける）。だから run は直列に回す。途中で止まっても続きから再開できるよう、終わった run は飛ばす。

### 判断の記録（`decision` イベント）
- エージェントの `events.jsonl` に、判断した瞬間ごとの `decision` 行を足す。段 1 のデータも、段 2 と同じ形で RL の検討に使えるようにするため。
- 判断の種類は 3 つとも記録する。どれを制御させるかは段 1 の結果を見て決める。
  1. 状態確認を、どの隣に、いつ送るか
  2. レコード取得を失敗したあとの、再送の待ち時間
  3. レコード取得の取得先と、同時に送る件数
- 各行には、判断の時点で見えていた状態を載せる。隣ごとの「通知された最大 seq」と「連続保持の範囲」、未取得の件数、送っている途中の件数、直前のタイムアウトの時刻など。そこに、選んだ行動と、**その行動を選んだ確率**も載せる。確率は off-policy 評価に必須。段 1 は既定の方針で決め打ちに選ぶので、確率は 1 になる。
- 正確な欄の形はチケット 02 で決め、この map に追記する。

### 指標の定義
- **発見までの時間**: (レコード, ノード) の組ごとに、origin の `record_created` からそのノードの `record_stored` まで。run の終わりまでに届かなかった組は捨てずに「打ち切り」として残す。集計では、届いた割合の時間変化（生存時間分析の形）と、打ち切りの割合を並べて出す。
- **全ノードが一致するまでの時間**: レコードごとに、最後のノードに届いた時刻まで。届かなかったノードがあれば打ち切り。
- **probe の発見率**: 分母は出した probe の数、分子は発見に成功した数。本体の取得は別に記録する。
- **制御の通信量**: `control_bytes_*` を、作られたレコード 1 件あたりに直す。

### 有効な run の判定
- 計測用の確認スクリプトを run ごとに走らせる。確かめるのは、前提が崩れていないこと。たとえば、全エージェントが起動して `counters` 行を書いた、put が成功した、予定どおりにレコードが作られた、生成した切断の予定どおりにリンクのイベントが記録された、など。
- 前提が崩れた run は捨てずに印をつけ、条件ごとの数を報告する。印のついた run が 5% を超える条件は、やり直す。
- 全体が収束したかどうかは、合否に使わない。切断率が高ければ届かないのは当然で、それは「結果」として扱う。
- 初期ベースラインの判定スクリプト（`semindex.check`）は、ホストの数が決まった形でないと受け付けないので、計測には使わない。`semindex.analyze` は台数にもトポロジーにも依存しないので、集計の部品として使える。

### データの置き場所
- run ごとに、計測と集計が読むものだけを `/home/lab_shared/semindex-eval/<段>/p<切断率>/<seed>/` に残す。`results.json`、各ノードの `events.jsonl`、生成した YAML とエージェント設定の 3 つ。
- `node_dirs` の残りは、run ごとに消す。Cefore の鍵があるから。
- リポジトリには、集計した表（CSV か Parquet）と図、集計のコマンドだけを、この effort の `evidence/` に入れる。

### 進め方
- 初期ベースラインと同じ。worker は sonnet。監査は worker と別系統（codex CLI の gpt-6.1-sol を read-only で、落ちていれば pi）。段階ごとの総括レビューは fable。sudo を要する Mininet の実行はオーケストレータが行う。
- 進捗は `PLAN.md` とボード。

### 実機で確かめたこと（2026-10-23）
- 5 ノードの直線（切断なし）を1回通した。全エージェントが起動し、h0 と h4 の 60 件が全ノードに届いた。発見までの時間の中央値は 1 ホストごとにおよそ 0.7〜0.9 秒延びる（チケット 01）。

### コードの読み取りで確かめたこと（2026-10-23）
- 5 ノードで `LOCAL_SOCK_ID` はぶつからない。テンプレートは h0〜h2 の 3 つだけだが、ReCefore はコピーしたあとに `LOCAL_SOCK_ID` をホスト番号に、`NODE_NAME` を `hN` に書き換える（ReCefore `src/runtime/template.py:122`, `:130`）。エージェントには自分のホストのディレクトリが `--cefore-conf-dir` で渡る。
- 同じ役割のテンプレートからコピーされたホスト（h1 と h3 など）は、鍵のファイルも同じものになる。この計測は署名を使わないので影響しない。
- `semindex.gen` は 5 ホスト、全ホストのエージェント、直線や木の `links`、複数の Index origin、どのホストからの probe にも対応している。本体を put する publisher は 1 台だけ。

## Fog

- `decision` 行を足したときの `events.jsonl` の大きさ。500 回分で何 GB になるかは、行の形が決まってから見積もる。
- p = 0.4 で、120 秒のうちにどれだけのレコードが届くか。打ち切りがほとんどになるなら、run を長くするか p の上限を下げる。

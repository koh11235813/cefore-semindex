## Task

短い試走で、間隔の選択肢の値と k を決める材料を出す（map の Fog）。オーケストレータが root で回す。

- 間隔: k = 1 で、間隔を 1 つに固定した方針（チケット 01 の選択肢を 1 つだけ与える。たとえば 0.5・1・2・4・8 秒）を、p = 0 と 0.4 で seed 数個ずつ回す。間隔ごとに、遅れ（とくに状態確認の待ち）と通信量がどれだけ動くかを見る。選択肢は、遅れと通信量の両方が目に見えて動く範囲から選ぶ。
- k: 既定の方針で、k = 1・2・4・8 を p = 0.4 で seed 数個ずつ回す。1 度に取る件数の分布がどう広がるかと、run 1 回の保存量を見る。
- 間隔のゆらぎをやめた影響（map の Fog）: 選択肢を与えた方針で、ノードどうしの状態確認が同じ時刻にそろい続けていないかを見る。
- 選んだ値と根拠を、段 2 の map の決定に書く。本番の条件（切断率、seed の数、run の長さ）の案も出す（決定は利用者）。

### 分かったこと

- 間隔: ゆらぎを入れた `t2j*` で、p = 0 の発見までの時間の中央値は 0.63 秒（0.5 秒）から 12.36 秒（10.043 秒）、制御の送信量／レコードは 6.63 KB から 1.46 KB まで動く。10.043 秒は p = 0.4 で 23 組が打ち切られる。この 4 つを本番の選択肢にした。
- ゆらぎ: ゆらぎ無しで固定した `t2i*` は位相が固定され（p = 0 で重なりが偶然の 2.8〜100 倍）、状態確認の待ちが間隔の 0.64〜0.87 倍と長めに出た。j = 0.1 の `t2j*` では 0.45〜0.57 倍で、位相は動き続ける。間隔ごとの遅れの基準は `t2j*`。
- k: k を増やしても 1 度に取る件数は広がらなかった（p = 0.4 の中央値はどの k でも 1 件）。k は供給を増やすつまみで、1 度に取る件数を決めるのは取得の側。k = 4 は上限 8 で回せる負荷に収まり（上限 32 と比べて発見までの時間の中央値 10.7 秒と 10.5 秒）、k = 8 はどちらの上限でも超える。
- 上限: 上流は Data をおよそ 35〜75 ms に 1 つ返し、上限を 32 にすると列の後ろのほうが Interest の lifetime（2 秒）に間に合わず、リンクがつながっていたのに起きた取得のタイムアウトが k = 8 で 82 回から 1343 回に増えた。上限は既定の 8 のまま。
- 選択肢の確かめ: 混ぜた方針では、選ばれた間隔の度数が一様と合い（χ² は自由度 3 で 2.86・3.33、自由度 4 で 3.69・4.02）、`action_prob` はすべて 1 / 選択肢の数だった。

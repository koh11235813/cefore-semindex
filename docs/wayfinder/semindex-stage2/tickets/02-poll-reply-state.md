## Task

`state_poll` の判断の状態に、その隣への直前の状態確認に返事が来たかと、続けて返事が来なかった回数を足す（map の「判断の状態に足すもの」）。

- 間隔の選択肢には Interest の lifetime（2 秒）より短いものがありうるので、判断の時点で直前の状態確認がまだ返事を待っていることがある。だから「来た」「来なかった（lifetime が過ぎた）」「まだ待っている」の 3 つを区別する。欄の名前と値の形は実装のときに決め、map の「判断の記録」の欄の形の書き方に合わせて段 2 の map に書く。
- 続けて返事が来なかった回数は、lifetime が過ぎた状態確認の連続回数。返事が 1 回来たら 0 に戻す。
- 状態確認の返事が来なかったことは、いまはどのイベントにも残っていない（`fetch_timeout` は取得だけ）。判断の状態に入れるのに加えて、イベントとしても残すかは実装のときに決める。
- 方針そのもの（送る Interest の列）は変えない。

## Acceptance

返事が来た場合、lifetime が過ぎた場合、まだ待っている場合、続けて来なかったあとに 1 回来た場合のそれぞれで、次の `state_poll` 行の状態の値を完全一致で確かめる。記録を止めた場合と比べて、送る Interest の列が一致することも確かめる。

## Resolution (2026-10-26)

- `feat/semindex-stage2` で実装した（`9e5533d`、返事の対応づけの修正 `a7637c9`）。欄は `last_poll_status`（`answered`・`timed_out`・`pending`、最初は `null`）と `consecutive_poll_timeouts`。決め方は map の「判断の記録の欄」に書いた。
- lifetime が過ぎたかは、エンジンが判断の時点で時計から決める（transport と同じ期限の式）。返事は名前の epoch_ms でどの状態確認への返事かを決める。最初の版は返事をいちばん新しい状態確認に結びつけていて、間隔が lifetime より短いと遅れた返事で状態を取り違えたので直した。
- 返事が来た、lifetime が過ぎた、まだ待っている、続けて来なかったあとに来た、古い状態確認への返事が新しい状態確認のあとに届いた、0.5 秒間隔で返事待ちが重なった、の各場合で、次の `state_poll` 行の値を完全一致で確かめた。記録を止めた場合と比べて Interest の列が一致することも試験にした。
- 返事は、届いた時点でその状態確認がいちばん新しいか、届いた時刻が送った時刻 + lifetime + 1 秒以下のときだけ受け付け、それ以外は無視する。受け付けられなくなった状態確認は記録から外して数だけ残すので、返事の来ない隣について記録が増え続けない。2000 秒の無応答でも記録が 7 件に収まること、期限ちょうどの返事は受け付け、それより後の返事は無視すること、送ったときはいちばん新しかった状態確認が次を送ったあとに期限を過ぎて返事を受けた場合に無視することを試験にした。
- 返事が来なかったことは、イベントとしては残さない。期限は送った時刻 + lifetime で決まり、次の `state_poll` 行に結果が載るため。

## Task

3 つの決め方（L: gemma-4-E2B を後から知った正解で調整したもの、M: ログから学んだもの、R: 式の決まり）を比べる。
まずなぞり直しの上で全部に点を付け、**決め方ごとに 1 つだけ選んだ候補**を実機に出す。

### この一手が示せること、示せないこと

**示せること**

1. **3 つの決め方の、主のマスでの実機の得と、その区間。**
2. **L と M の差。** 同じ入力、同じ瞬間、同じ物差しの上での差。
3. **なぞり直しの点が、実機の点を言い当てたか。**

**示せないこと**

- **3 つの決め方の一般の順位。** 1 つのマス、1 つの負荷、3 つの腕、40 seed の上の結果にとどまる。
- **「not seen」が上積みの無さを示すこと。** 示さない。区間の幅が効きより広いという意味にとどまる。
- **先を知っている方針 V との差が埋まるか。** なぞり直しでは `V_at_F − F = +70.1 ポイント`（区間 +63.9〜+76.1、
  `evidence/18/bound.md` の「The reading, under the rule spec.md fixed before the numbers」の表）だが、V はレコードの作られる時刻と切断の時刻表を知っている。
  この差し引きの F は `F_reach`（+8.9）で、チケット 07 が固定する `F_restricted`（+10.7）ではない。
- **細かい刻みでの良さ。** 腕は 3 つに固定する。

### 解けていない問題 2 つ

**この 2 つが解けないと、実機の run は始まらない。** 両方、今は答えが無い。

1. **実機に決め方を差し込む口が無い。** 今の実機のコードの状態確認の間隔の決め方は、`SyncConfig` のどの欄が埋まっているかで選ばれる 4 つの排他の方式だけ。決まりは状態をほとんど見ず、判断の状態の dict は**選んだ後に**記録のために組み立てられる。だから「状態を読んで腕を返す外の決め方」を呼ぶ道が 1 本も無い。src の変更が要る。どれだけの変更になるかは**見積もっていない**。
2. **1 回の判断の推論にかかる時間。** ノードの判断は 100 ms ごとに刻む同期の周回の中で起きる。L も M も、1 回の判断につき 1 回の推論が入る。チケット 10 の合否の線 5 とチケット 11 の線 6 がその時間を測って報告するので、その数を見てから、どう置くかを決める。収まらないなら別の置き方（前もって表に展開する、周回の外に出す）を考えることになるが、どれもまだ考えていない。

## 下調べで分かったこと（2026-11-27）

- **実機の口は、上の「解けていない問題」の 1 が書くより近い。** チケット 08 の方式は、解決の時点で、なぞり直しの口と同じ 6 つの欄の状態をもう組んでいる
  （`src/semindex/engine.py` の 680〜684 行）。ただし乱数で引く行（674 行）が状態を組む行より前にある。
  送信の時点では状態を組むのが選んだ後になるが、L も M も送信の時点では状態を読まない（その組が前に選んだ間隔を返す）ので、この順は効かない。
- **実機が持っていない入力は 1 つだけである。** なぞり直しの口は、その組の直近 8 回の交換の履歴を決め方に渡す。engine はそれを持っていない
  （`evidence/13/replay.py` の 85〜93 行が、元の実装には無いと書いている）。履歴の 1 行に要る値は、判断の記録を書く所（`engine.py` の 692〜707 行）にそろっている。
- **ノードは thread 1 本の周回で動く。** 受信の待ち（最大 100 ms、1 個だけ受ける）、状態確認の送信と時間切れの判定、記録の作成が、同じ周回に並ぶ。
  判断の中で推論を待つと、その間は隣からの問い合わせにも答えられない。ADR 0004 が直した欠陥（周回の中で本体を同期して取り、状態確認が約 1 秒遅れた）と同じ形になる。
- **この機械では L を動かせない。** GPU が無く、ノードの venv に torch も無い（numpy はある）。`hpc-debian` の GPU（RTX PRO 5000 Blackwell）は空いていて、
  この機械からの往復は平均 0.457 ms だった（ping 10 回）。CPU の上での L の時間は、誰も測っていない。
- **ノードの中から、共有の file system 上の socket に届く。** ReCefore がノードの process を起こすのと同じ道（Mininet の `host.popen`）で起こした process から、
  外の process が開いた socket へ 2000 回往復し、中央 0.018 ms、p99 0.028 ms、最大 0.452 ms だった。外の機械の loopback の TCP には届かない（接続を断られる）。
  socket の path は 108 byte までで、長い path は開けない。
- **次の送信の時刻は「前の送信の時刻 + 間隔」で決まる**（`engine.py` の 690〜691 行）。答えが届くのが遅れても、次の送信より前に届けば、送信の時刻は待った場合と同じになる。
  余りがいちばん小さいのは、時間切れで解決した 3.695 秒の腕で、およそ 1.33 秒である（3.695 × 0.9 − 2.0）。
- **基準の 5 段と今の版の間に、`src` の commit が 1 つある**（`1c3f758`、チケット 08 の方式）。
- **seed 121〜160 の予測のなぞり直しには先例がある。** チケット 07 の `evidence/20/predict.py` は、学習側の門（`evidence/22/port.py` の `check_seeds`）を通らない専用の台本で、
  seed から切断と記録の時刻表を作り、時計は seed 1〜20 の run から借りている。実機の run は要らない。
- **`evalvalid` は間隔を何も確かめていない。** Acceptance 5 は、新しい確かめを書く事になる。

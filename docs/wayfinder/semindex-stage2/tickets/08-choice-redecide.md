## Task

選択肢をばらばらに引く方式（`state_poll_interval_choices_s`）に、**返事が来たときと時間切れになったときに引き直す**道を足して、
その方式でランダムに引いた段を回し、ログから学ぶ ML の材料にする。
この案は 2026-11-22 に書き、同じ日に利用者が認めた（下の「決まったこと」）。

**なぜ引き直しが要るか。** 今の選択肢の方式は、N+1 回目の間隔を N 回目の**送信の時点で**引く
（`src/semindex/engine.py:665-680`）。だから `state_poll` の行に乗る `last_poll_status` と
`consecutive_poll_timeouts` は、N-1 回目の結果を指している（`engine.py:487-489` の注記）。
決まりの方式（`state_poll_rule`）では送信時の間隔は仮で、解決した時点の引き直しが本当の判断になっている
（`engine.py:521-525`）。3 つの決め方を比べるなら、**3 つが同じ瞬間に同じ入力を見て決めなければならない。**
今のままだと、ML と gemma が学ぶ判断の時刻が、決まりの判断の時刻と 1 回ずれる。

- **(a) 3 つの決め方の判断の時刻と入力をそろえる。** 引き直しを解決の時点に置けば、
  式の決まりが見る状態と、学習の側が見る状態が同じになる。
- **(b) ML が学ぶデータを、確率つきで残す。** 引き直しは一様に引き、`action_prob` に 1/3 を書く。
  これが無いと、ログから方針を組み立てる側に重みの付け所が無い。
- **(c) 判断の行に、ノードが自分で見られる状態を全部乗せる。** 今の引き直しの行は
  `{last_poll_status, consecutive_poll_timeouts}` の 2 欄だけで、`tracker.decision_state(neighbor)` を呼んでいない
  （`engine.py:636-640` とその注記）。この 2 欄だけでは、ML も gemma も origin ごとの進み具合を見られない。

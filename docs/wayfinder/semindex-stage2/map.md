# Semantic Index 計測（段 2：学習制御のためのデータ集め）

## Destination

段 1（`docs/wayfinder/semindex-eval/`）と同じ直線 5 ノードで、状態確認の間隔をエージェントが確率で選ぶ形にして run を回し、判断ごとの状態・行動・その行動を選んだ確率・あとから計算できる報酬の材料をそろえる。集めたデータで、index の状態制御に学習制御を使えるかを検討できるところまでがこの effort。

方針を学ぶこと、学んだ方針を評価して採否を決めることは目的に含めない。どの方向で学ぶか（ベイズ最適化、文脈つきバンディット、オフライン RL）は、このデータを見てから決める。

## Notes

- 実行（execution）型の effort。エージェントと生成器を変え、run を回し、集計まで行う。
- 前提は段 1 の effort（チケット 01〜06 が closed、結果はチケット 06 の Resolution と `evidence/06/`）。トポロジー、計測の窓、切断の起こし方、有効な run の判定、データの置き場所は、段 1 の map の決定をそのまま使う。変えるものだけをこの map に書く。
- 用語は `CONTEXT.md`、構造的な決定は `docs/adr/`。
- 対象外: 方針の学習と評価、名前の重要度による重みづけ（定義がまだ無い）、通知にレコードの属性を載せるといったプロトコルの変更、取得の計画と再送の待ち時間を確率で選ぶこと、トポロジーを変える計測。

## Decisions so far

### 制御させる判断（2026-10-26 決定）
- 状態確認の間隔だけを確率で選ばせる。段 1 の結果で、判断の数が最も多く、どの切断率でも同じだけ出るのがこの判断だったため（段 1 のチケット 06 の Resolution）。
- 取得の計画（取得先と 1 度に取る件数）と再送の待ち時間は、段 1 と同じ既定の方針のまま。再送の待ち時間は、段 1 の 500 回で判断が 27 件しか出ず、データが足りない。

### 行動と確率（2026-10-26 決定）
- 間隔は、いくつかの離散的な値（たとえば 1・2・4 秒）から選ぶ。段 1 のような連続の一様乱数では、選んだ確率が密度になって off-policy 評価で扱いにくいため。
- 集めるときの方針は、選択肢を一様の確率で選ぶ（3 択なら 1/3 ずつ）。ベイズの方針や ε-greedy は使わない。
  - 確率を固定すれば、その値をそのまま `action_prob` に書ける。学びながら確率を変える方針では、各判断の確率を数値で見積もる必要があり、良さそうな行動に偏ってほかの行動のデータが減る。
  - エミュレータの中なので、一様に選んで性能が一時的に落ちても困る人はいない。一様にすると、どの行動のデータも同じだけ集まり、off-policy 評価の 1 判断あたりの重要度比の最大値も選択肢の数で抑えられる（判断の列にわたって比を掛ける評価では、判断の数に応じて指数的に大きくなる）。
- 選ぶのは隣ごと、状態確認を送るたびに 1 回。`decision` 行の形（`state`・`action`・`action_prob`）は段 1 のまま使い、`action_prob` に実際の確率を書く。

### 本番の間隔の選択肢（2026-10-26、チケット 04 で決定）
- 本番は {0.5, 1.359, 3.695, 10.043} 秒（0.5·eⁿ、n = 0〜3、小数 3 桁）を一様に選ぶ。`action_prob` は 0.25、ゆらぎは j = 0.1（「選択肢の間隔のゆらぎ」）。
- この 4 つで、遅れと通信量の両端をおさえられる。ゆらぎを入れて間隔を 1 つに固定した試走（`t2j*`、seed 3 個ずつ）では、p = 0 の発見までの時間の中央値が 0.63 秒（0.5 秒）から 12.36 秒（10.043 秒）まで約 20 倍、制御の送信量／レコード（グループ名の長さをそろえた値）が 6.63 KB から 1.46 KB まで約 4.5 倍動いた。数字は `evidence/04/`。
- 10.043 秒は、p = 0.4 で発見の組が 23 組打ち切られる（窓の 120 秒のうちに届かない）。それでも通信量のいちばん少ない端として残す。打ち切りは Kaplan–Meier で扱う（段 1 と同じ）。

### 判断の状態に足すもの（2026-10-26 決定）
- `state_poll` の判断の状態に、その隣への直前の状態確認に返事が来たかと、続けて返事が来なかった回数を足す。
- 段 1 の内訳（下の「段 1 のデータで数えたこと」）では、リンクが戻ってから次の状態確認までの待ちが、p = 0.4 で 1 ホストあたり平均 502 ms ある。エージェントはリンクが戻ったことを直接は知らないので、返事の来なかった状態確認の履歴を使ってこの待ちをどれだけ減らせるかは、段 2 で確かめる仮説。いまの状態にある `last_timeout_s` は取得のタイムアウトだけで、状態確認の返事が来なかったことは方針から見えない。足さないと、状態に応じて間隔を変える方針を段 2 のデータで評価できない。

### 判断の記録の欄（2026-10-26、チケット 01・02 で決定）
- 段 1 の map の「判断の記録」の欄の形に、次を足す。足さないものは段 1 のまま。
- 間隔の選択肢は、エージェント設定の `state_poll_interval_choices_s`（有限の正の数の列。空と重複は受け付けない。重複があると `action_prob` が実際の確率と合わなくなるため。NaN や無限大は、次の状態確認の時刻が来なくなるので、エージェント設定でも生成の時点でも受け付けない）。与えると、隣ごと・状態確認を送るたびに一様に 1 つ選び、`action` の `interval_s` にその値、`action_prob` に 1 / 選択肢の数を書く。選択肢が 1 つなら決め打ちの間隔で、`action_prob` は 1。選択肢の方針は段 1 のゆらぎ（`state_poll_jitter_frac`）を使わないので、`state_poll_interval_s`・`state_poll_jitter_frac` と一緒には与えられない。選択肢の方針のゆらぎは、下の「選択肢の間隔のゆらぎ」。
- 選ぶための乱数は、エージェント設定の `seed`（run の seed をそのまま書く）とノード名から決める。選択肢を与えるときは `seed` が必須。生成器が `seed` と選択肢をエージェント設定に書くのはチケット 03。
- 選択肢を与えないときは段 1 と同じ（2 秒 ± 20%、`action_prob` は 1）。
- `state_poll` の `state` に 2 つ足す（ほかの種類の `state` は段 1 のまま）。どちらも、判断の相手の隣への状態確認についての値で、いま送る状態確認の前の時点のもの。
  - `last_poll_status`: 直前の状態確認が `"answered"`（返事が来た）・`"timed_out"`（返事が来ないまま lifetime が過ぎた）・`"pending"`（まだ lifetime が過ぎていない）のどれか。その隣への最初の状態確認では `null`。
  - `consecutive_poll_timeouts`: 返事の来た状態確認のうちいちばん新しいものより後に送った状態確認で、返事が来ないまま lifetime が過ぎたものの数（まだ待っているものは数えない）。古い状態確認への返事が遅れて届いても、それより新しい状態確認がもう lifetime を過ぎていれば 0 には戻らない。
  - lifetime が過ぎたかは、エンジンが判断の時点で時計から決める（送った時刻 + `interest_lifetime_ms` ≤ いま。cefpyco の transport の期限と同じ式）。transport の期限切れの通知は、`on_tick` より前に読んだ時刻で走るので、ちょうど期限の境目で判断すると「まだ待っている」に見えてしまうため。
  - 返事は、名前の epoch_ms で、どの状態確認への返事かを決める（transport が名前から取り出して `on_state` に渡す）。間隔が lifetime より短いと返事待ちの状態確認が同時にいくつもあり、遅れて届いた古い状態確認への返事を新しい状態確認への返事と取り違えないため。lifetime が過ぎてから届いた返事も「来た」に数え、中身を読めない返事も「来た」に数える。ただし返事を受け付けるのは、届いた時点でその状態確認がいちばん新しいか、届いた時刻が送った時刻 + lifetime + 1 秒（Cefore が PIT の項目を消すまでの時間）以下のときだけで、それ以外の返事は無視する（その状態確認は「来なかった」のまま）。この条件で受け付けられなくなった状態確認は記録から外して数だけ残すので、返事の来ない隣について持つ記録は、止まっていた時間によらず lifetime + 1 秒に収まる数で済む。
  - 返事が来なかったことをイベントとしては残さない。期限の時刻は送った時刻 + lifetime で、次の `state_poll` 行に結果が載るので、別の行を足しても新しい情報が無いため。

### 生成器と集計（2026-10-26、チケット 03 で決定）
- run の名前とグループ名の p は、3 桁の百分率で書く（p = 0 → `p000`、0.1 → `p010`、0.4 → `p040`）。どの p でも長さが同じで、段 1 の `p0.1`〜`p0.4` とも同じ 4 文字なので、p > 0 の通信量は段 1 と同じ長さの名前で比べられる。0.01 の倍数でない p は、2 つの p が同じ名前になるので受け付けない。保存先の名前（`p0/`、`p0.1/` など）は段 1 のまま。
- k は、生成の時刻（段 1 と同じ origin ごとに 30 回、2 秒おき）1 回あたりのレコードの数。窓と生成の時刻は変えないので、origin ごとのレコードは 30k 件になる。属性はレコードごとに seed から引く（同じ流れから順に引くので、k = 1 なら段 1 と同じ値）。
- 間隔の選択肢は、生成器の `--interval-choices` から実験の記述の `state_poll_interval_choices_s` を通り、各エージェント設定に、run の seed（`seed`）と一緒に書く。与えないときは、どちらもエージェント設定に書かない（k = 1 なら段 1 と同じ設定になる）。
- 回し手（`--k`・`--interval-choices`・`--choice-jitter`）は、k と選択肢とゆらぎの幅 j を `meta.json` の `k`・`state_poll_interval_choices_s`・`state_poll_choice_jitter_frac` に残す。保存先の道のりには入らないので、値を変えるときは `--stage` を変える。集計は `runs.csv` の末尾の 5 列のうち前の 3 列に出す。記録の無い run では空で、j の列はゆらぎを入れる前の run でも空。残りの 2 列は、次の 2 項の上限と `PRAGMA synchronous` の値。
- 回し手は `--max-in-flight` も受ける（2026-10-26 決定）。隣ごとに同時に出しておく取得の Interest の上限（エージェント設定の `max_in_flight_per_neighbor`、1 以上の整数）で、与えると各エージェント設定に書き、`meta.json` の `max_in_flight_per_neighbor` と `runs.csv` の最後から 2 番目の列に残す（記録の無い run では空）。与えないときはエージェント設定に何も書かず、エージェントの既定の 8 のまま。保存先の道のりには入らないので、値を変えるときは `--stage` を変える。
- 回し手は `--store-synchronous`（`FULL`・`NORMAL`・`OFF` のどれか）も受ける（2026-10-29 決定）。与えると各エージェント設定の `store_synchronous` に書き、エージェントは自分の `index.db` を開くときに `PRAGMA synchronous` をその値にする。`meta.json` の `store_synchronous` と `runs.csv` の最後の列に残す（記録の無い run では空）。与えないときはエージェント設定に何も書かず、PRAGMA も出さないので、SQLite の既定の `FULL` のまま。受け取ったレコードの扱いに 1 件あたり数十 ms かかっている（単独の取得は 1〜2 ms で返る）のが、レコードごとのトランザクションの確定で毎回 fsync しているせいかを、`NORMAL`（WAL ではチェックポイントのときだけ fsync する）で回して確かめるために足した。保存先の道のりには入らないので、値を変えるときは `--stage` を変える。
- 集計の `decisions.csv` には、段 2 のエージェントが書いた `state_poll` の行があるときだけ、`action_prob` と `consecutive_poll_timeouts`（中央値と四分位）、`last_poll_status=<値>` の頻度（`null`・`answered`・`timed_out`・`pending` の順）を足す。pilot2 を元のコードと集計し直して比べ、`runs.csv` 以外の CSV と PNG の図がバイト単位で同じ、PDF の図は `CreationDate` を除いて同じ、`runs.csv` は足した列（空）を除いて同じことを確かめた。

### 選択肢の間隔のゆらぎ（2026-10-26 決定）
- 試走で、間隔を 0.5 秒に固定すると、全エージェントの状態確認が同じ時刻にそろい続けた（エージェントの起動は 17 ms ほどの差しかなく、同じ周期でゆらぎが無いと位相がずれない。重なりの割合は偶然なら 0.20 のところ 0.75）。この map の Fog に書いた「選び直すならそろい続けることはない」という見込みは、選択肢が 1 つのときは外れた。選択肢が 0.5 秒の倍数ばかりだと混ぜても共通の格子に乗る、とも見ていたが、0.5〜8 秒を一様に混ぜた試走（ゆらぎ無し）では、重なりは偶然の 1.3〜1.7 倍、そろったまま次の状態確認に進む割合は 21〜29% で、そろい続けはしなかった（2026-10-26 追記）。そろい続けるのは、同じ値を選び続けるときだけ。
- 試走で確かめた（2026-10-26 追記、チケット 04）: ゆらぎ無しで間隔を固定した `t2i*` は、どの間隔でも位相が固定された。p = 0 で重なりは偶然の 2.8〜100 倍（p = 0.4 でも 1.3〜42 倍）、相手とのずれの変わり方（offset drift）は 1 回あたり 1〜35 ms。j = 0.1 の `t2j*` では、重なりは偶然の 0.65〜2.0 倍で、offset drift は 41〜1406 ms と位相が動き続ける。10.043 秒だけは 0〜5.3 倍と幅があるが、状態確認が 3 run で 290 回しかなく偶然の重なりが 0.010 なので、数回の重なりで比が大きく振れているだけで、続けて重なる割合は 0。続けて重なる割合は 3.695 秒・10.043 秒・混ぜた方針で 0〜0.27、0.5 秒で 0.46〜0.60、1.359 秒で 0.33〜0.39（間隔が短いと ±50 ms の窓に対してずれの動きが小さいため）。
  - 1 ホストあたりの状態確認の待ち ÷ 間隔は、p = 0 で `t2i*` が 0.64〜0.87、`t2j*` が 0.45〜0.57。そろっていると、上流がレコードを保存する時刻と下流が状態確認を送る時刻の関係が run の間ずっと変わらないので、待ちが間隔の半分前後にならされず、長いほうに偏ることがある。だから `t2i*` の遅れは大きめに出ていて、間隔ごとの遅れの基準は `t2j*`。
- 選択肢の方針では、選んだ間隔に、状態確認ごとに [1 − j, 1 + j] の一様な係数を掛けて使う。既定は j = 0.1。次の状態確認は、この状態確認を送った時刻 + ゆらいだ間隔で、前のゆらぎを打ち消さない（位相がずれていくことが目的なので）。
  - 行動は選んだ値のまま。`action` の `interval_s` は選んだ値、`action_prob` は 1 / 選択肢の数のままで、実際に使った間隔を `applied_interval_s` に足す。ゆらぎは行動の選び方ではなく、行動の実行の仕方なので、`action_prob` には入れない。
  - ゆらぎの乱数は、選択肢の乱数とは別の流れで、run の seed とノード名から決める。記録の有無によらず、状態確認ごとにちょうど 1 回引く。
  - 設定のキーは `state_poll_choice_jitter_frac`（0 以上 1 未満の有限の数。選択肢を与えたときだけ受け付ける）。段 1 の `state_poll_jitter_frac` は使い回さない。既定が段 1 は 0.2、選択肢の方針は 0.1 と違い、選択肢との併用は誤りとして受け付けない、という段 1 の決まりも変えずに済むため。j = 0 で、ゆらぎを入れる前の選択肢の方針とまったく同じ時刻に送る（`decision` 行には `applied_interval_s` が増える）。
  - 生成器と回し手は、選択肢を与えたときに j（与えなければ 0.1）をエージェント設定と `meta.json` に必ず書く。選択肢を与えないときはエージェント設定に何も書かず（`meta.json` には null を書く）、段 1 の方針はそのまま。
- 選択肢の値は、比が無理数になるものを使う（利用者の希望）。たとえば 0.5·eⁿ（0.5、1.359、3.695、10.04 秒）。混ぜた方針が共通の格子に乗らないようにするため、と考えていたが、上のとおり試走では格子によるそろいは見えなかった（2026-10-26 追記）。比が無理数でも害は無いので、この決まりは残す。そろいを崩すのは、ゆらぎのほう。これは使い方の決まりで、コードは値を制限しない（`--interval-choices` はこうした小数をそのまま受け、`meta.json` と `runs.csv` でも同じ値に戻ることを試験にした）。

### 報酬の材料（2026-10-26 決定）
- 報酬は「遅れ」と「制御の通信量」の重みづけで組む。遅れには、ホップ数が多いほど重い重みを掛ける。
- ホップ数の重みは集計の側で掛ける。エージェントは判断の時点でホップ数を知らない（判断の状態にあるのは origin ごとの進み具合と隣の通知だけ）が、集計はトポロジーを知っている。報酬の式そのものと重みの値は、学ぶ段で決めればよい。この effort では、どの式にも使える材料（レコードとノードの組ごとの遅れ、ホップ数、通信量）を残す。
- 名前の重要度による重みは、この effort では入れない。重要度の定義がまだ無く、取得は (origin, seq) で送るのでレコードの属性は届くまで分からず、方針の入力にするにはプロトコルの変更が要るため。

### 負荷（2026-10-26 決定）
- origin は段 1 と同じ h0 と h4 の 2 つのまま、1 回の生成で k 件のレコードを作る。段 1 では 1 度に取る件数がほとんど 1 件で、取得の計画に幅が無かったため。
  - 2026-10-26 訂正（チケット 04 の試走）: この理由は外れた。k を増やしても 1 度に取る件数は広がらず、p = 0.4 の中央値は k = 1〜8 のどれでも 1 件、2 件以上の計画の割合は k = 8 で 10% まで下がった。k は供給を増やすつまみで、1 度に取る件数を決めるのは取得の側（隣ごとの同時取得の上限と、計画の時点で分かっている足りないレコードの数）。1 度に取る件数を広げたのは、むしろ長い間隔で、p = 0 の中央値は 10.043 秒で 5 件。k を増やす理由は、1 run あたりのレコード（判断と報酬の材料）を増やし、取得の側が詰まらない範囲で負荷を上げること、と読み替える。
- 本番は k = 4、隣ごとの同時取得の上限（`max_in_flight_per_neighbor`）は既定の 8 のまま（2026-10-26、チケット 04 で決定）。
  - k = 4 は、上限 8 で回せる負荷に収まる。p = 0.4 で上限を 8 と 32 にして比べると、発見までの時間の中央値は 10.7 秒と 10.5 秒、打ち切りは 6 組と 0 組で、上限を上げてもほとんど変わらない。
  - k = 8 は、どちらの上限でも回せる負荷を超える。上限 8 で 27.5 秒・打ち切り 608 組、上限 32 で 22.2 秒・打ち切り 177 組。
  - 上限を上げると、取得のタイムアウトが増える。k = 8 で上限を 8 から 32 にすると、直前の 2 秒ずっとリンクがつながっていたのに起きたタイムアウトが 82 回から 1343 回に増えた。上流は Data をおよそ 60 ms に 1 つしか返していない（h1〜h3 で続く `record_stored` の間隔の中央値は、k = 4 で上限 8 が 50 ms・上限 32 が 34 ms、k = 8 で上限 8 が 75 ms・上限 32 が 58 ms、k = 1・2 は 34 ms）。31 件が列に並ぶと 31 × 60 ms ≈ 1.9 秒で、Interest の lifetime の 2 秒とほぼ同じになり、列の後ろのほうが lifetime 切れになる。上限の天井は、上限 × Data 1 つを返す時間 < Interest の lifetime。
  - 取得のタイムアウトは、ほぼすべて送ってから 2.0〜2.75 秒で起きている（lifetime 切れ。4 段 4513 回のうち 13 回だけがそれより遅く、最大 3.58 秒）。再送の待ちは 2・4・8・16 秒。数字は `evidence/04/` の `capcheck.py`。
- エージェントは時刻が来た予定をまとめて全部レコードにする（`agent.py` の `_drain_schedule`）ので、生成器が同じ `at_s` の予定を k 件並べればよく、エージェントの変更は要らない。
- origin を 9 つ以上に増やす案は採らない。判断の状態に載る origin は最大 8 つで、超えると `truncated` になって状態の一部が記録から落ちる。
- 負荷が段 1 と違うので、段 1 の数字とは直接比べない。同じ負荷で、既定の方針（間隔 2 秒 ± 20%）の基準も回す。

### 段 1 のデータで数えたこと（2026-10-26）
- 段 1 のチケット 06 の Resolution に書いた 2 つの推測を、s1 の 500 回で数えた。表と定義は `evidence/s1-breakdown/`。
- 切断で増える遅れの 90〜94% は、上流がレコードを持っているのにリンクが落ちていた時間で、状態確認の間隔では縮められない。状態確認の待ちは、1 ホストあたり平均 1038 ms（p = 0）から 1059 ms（p = 0.4）でほとんど変わらない。リンクが戻ったあとの待ちは、ふだんの待ちと置き換わるだけ。
- それでも、状態確認の間隔は遅れのうち方針で動かせるほぼ唯一の部分。p = 0 では遅れの 99%、p = 0.4 でも 26% が状態確認の待ちで、平均はおよそ間隔の半分。間隔を縮めれば、この部分はどの p でも同じように縮むと見ている。
- 通信量が p とともに減るのは、リンクが落ちている間に送った状態確認に返事が来ないため。取得の回数はどの p でも同じで、減るのは取得の判断の数（1 回の判断でまとめて取る）。p = 0 の通信量は、グループ名が 2 文字短いぶんおよそ 47 B／レコード少なく出ている。
- 間隔の効きが p によらないなら、状態によって間隔を変える方針は、決まった間隔に勝ちにくい。そのときは学ぶ段の方向として、ベイズ最適化で間隔を決めれば足りるかもしれない。状態に応じて変える価値がありそうなのは、返事の来なかった状態確認のあと（「判断の状態に足すもの」）。

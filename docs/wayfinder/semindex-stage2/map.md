# Semantic Index 計測（段 2：学習制御のためのデータ集め）

## Destination

段 1（`docs/wayfinder/semindex-eval/`）と同じ直線 5 ノードで、状態確認の間隔をエージェントが確率で選ぶ形にして run を回し、判断ごとの状態・行動・その行動を選んだ確率・あとから計算できる報酬の材料をそろえる。集めたデータで、index の状態制御に学習制御を使えるかを検討できるところまでがこの effort。

方針を学ぶこと、学んだ方針を評価して採否を決めることは目的に含めない。どの方向で学ぶか（ベイズ最適化、文脈つきバンディット、オフライン RL）は、このデータを見てから決める。

## Notes

- 実行（execution）型の effort。エージェントと生成器を変え、run を回し、集計まで行う。
- 前提は段 1 の effort（チケット 01〜06 が closed、結果はチケット 06 の Resolution と `evidence/06/`）。トポロジー、計測の窓、切断の起こし方、有効な run の判定、データの置き場所は、段 1 の map の決定をそのまま使う。変えるものだけをこの map に書く。
- 用語は `CONTEXT.md`、構造的な決定は `docs/adr/`。
- 対象外: 方針の学習と評価、名前の重要度による重みづけ（定義がまだ無い）、通知にレコードの属性を載せるといったプロトコルの変更、取得の計画と再送の待ち時間を確率で選ぶこと、トポロジーを変える計測。

## Decisions so far

### 制御させる判断（2026-10-26 決定）
- 状態確認の間隔だけを確率で選ばせる。段 1 の結果で、判断の数が最も多く、どの切断率でも同じだけ出るのがこの判断だったため（段 1 のチケット 06 の Resolution）。
- 取得の計画（取得先と 1 度に取る件数）と再送の待ち時間は、段 1 と同じ既定の方針のまま。再送の待ち時間は、段 1 の 500 回で判断が 27 件しか出ず、データが足りない。

### 行動と確率（2026-10-26 決定）
- 間隔は、いくつかの離散的な値（たとえば 1・2・4 秒）から選ぶ。段 1 のような連続の一様乱数では、選んだ確率が密度になって off-policy 評価で扱いにくいため。
- 集めるときの方針は、選択肢を一様の確率で選ぶ（3 択なら 1/3 ずつ）。ベイズの方針や ε-greedy は使わない。
  - 確率を固定すれば、その値をそのまま `action_prob` に書ける。学びながら確率を変える方針では、各判断の確率を数値で見積もる必要があり、良さそうな行動に偏ってほかの行動のデータが減る。
  - エミュレータの中なので、一様に選んで性能が一時的に落ちても困る人はいない。一様にすると、どの行動のデータも同じだけ集まり、off-policy 評価の 1 判断あたりの重要度比の最大値も選択肢の数で抑えられる（判断の列にわたって比を掛ける評価では、判断の数に応じて指数的に大きくなる）。
- 選ぶのは隣ごと、状態確認を送るたびに 1 回。`decision` 行の形（`state`・`action`・`action_prob`）は段 1 のまま使い、`action_prob` に実際の確率を書く。

### 判断の状態に足すもの（2026-10-26 決定）
- `state_poll` の判断の状態に、その隣への直前の状態確認に返事が来たかと、続けて返事が来なかった回数を足す。
- 段 1 の内訳（下の「段 1 のデータで数えたこと」）では、リンクが戻ってから次の状態確認までの待ちが、p = 0.4 で 1 ホストあたり平均 502 ms ある。エージェントはリンクが戻ったことを直接は知らないので、返事の来なかった状態確認の履歴を使ってこの待ちをどれだけ減らせるかは、段 2 で確かめる仮説。いまの状態にある `last_timeout_s` は取得のタイムアウトだけで、状態確認の返事が来なかったことは方針から見えない。足さないと、状態に応じて間隔を変える方針を段 2 のデータで評価できない。

### 判断の記録の欄（2026-10-26、チケット 01・02 で決定）
- 段 1 の map の「判断の記録」の欄の形に、次を足す。足さないものは段 1 のまま。
- 間隔の選択肢は、エージェント設定の `state_poll_interval_choices_s`（有限の正の数の列。空と重複は受け付けない。重複があると `action_prob` が実際の確率と合わなくなるため。NaN や無限大は、次の状態確認の時刻が来なくなるので、エージェント設定でも生成の時点でも受け付けない）。与えると、隣ごと・状態確認を送るたびに一様に 1 つ選び、`action` の `interval_s` にその値、`action_prob` に 1 / 選択肢の数を書く。選択肢が 1 つなら決め打ちの間隔で、`action_prob` は 1。選択肢の方針はゆらぎを使わないので、`state_poll_interval_s`・`state_poll_jitter_frac` と一緒には与えられない。
- 選ぶための乱数は、エージェント設定の `seed`（run の seed をそのまま書く）とノード名から決める。選択肢を与えるときは `seed` が必須。生成器が `seed` と選択肢をエージェント設定に書くのはチケット 03。
- 選択肢を与えないときは段 1 と同じ（2 秒 ± 20%、`action_prob` は 1）。
- `state_poll` の `state` に 2 つ足す（ほかの種類の `state` は段 1 のまま）。どちらも、判断の相手の隣への状態確認についての値で、いま送る状態確認の前の時点のもの。
  - `last_poll_status`: 直前の状態確認が `"answered"`（返事が来た）・`"timed_out"`（返事が来ないまま lifetime が過ぎた）・`"pending"`（まだ lifetime が過ぎていない）のどれか。その隣への最初の状態確認では `null`。
  - `consecutive_poll_timeouts`: 返事の来た状態確認のうちいちばん新しいものより後に送った状態確認で、返事が来ないまま lifetime が過ぎたものの数（まだ待っているものは数えない）。古い状態確認への返事が遅れて届いても、それより新しい状態確認がもう lifetime を過ぎていれば 0 には戻らない。
  - lifetime が過ぎたかは、エンジンが判断の時点で時計から決める（送った時刻 + `interest_lifetime_ms` ≤ いま。cefpyco の transport の期限と同じ式）。transport の期限切れの通知は、`on_tick` より前に読んだ時刻で走るので、ちょうど期限の境目で判断すると「まだ待っている」に見えてしまうため。
  - 返事は、名前の epoch_ms で、どの状態確認への返事かを決める（transport が名前から取り出して `on_state` に渡す）。間隔が lifetime より短いと返事待ちの状態確認が同時にいくつもあり、遅れて届いた古い状態確認への返事を新しい状態確認への返事と取り違えないため。lifetime が過ぎてから届いた返事も「来た」に数え、中身を読めない返事も「来た」に数える。ただし返事を受け付けるのは、届いた時点でその状態確認がいちばん新しいか、届いた時刻が送った時刻 + lifetime + 1 秒（Cefore が PIT の項目を消すまでの時間）以下のときだけで、それ以外の返事は無視する（その状態確認は「来なかった」のまま）。この条件で受け付けられなくなった状態確認は記録から外して数だけ残すので、返事の来ない隣について持つ記録は、止まっていた時間によらず lifetime + 1 秒に収まる数で済む。
  - 返事が来なかったことをイベントとしては残さない。期限の時刻は送った時刻 + lifetime で、次の `state_poll` 行に結果が載るので、別の行を足しても新しい情報が無いため。

### 生成器と集計（2026-10-26、チケット 03 で決定）
- run の名前とグループ名の p は、3 桁の百分率で書く（p = 0 → `p000`、0.1 → `p010`、0.4 → `p040`）。どの p でも長さが同じで、段 1 の `p0.1`〜`p0.4` とも同じ 4 文字なので、p > 0 の通信量は段 1 と同じ長さの名前で比べられる。0.01 の倍数でない p は、2 つの p が同じ名前になるので受け付けない。保存先の名前（`p0/`、`p0.1/` など）は段 1 のまま。
- k は、生成の時刻（段 1 と同じ origin ごとに 30 回、2 秒おき）1 回あたりのレコードの数。窓と生成の時刻は変えないので、origin ごとのレコードは 30k 件になる。属性はレコードごとに seed から引く（同じ流れから順に引くので、k = 1 なら段 1 と同じ値）。
- 間隔の選択肢は、生成器の `--interval-choices` から実験の記述の `state_poll_interval_choices_s` を通り、各エージェント設定に、run の seed（`seed`）と一緒に書く。与えないときは、どちらもエージェント設定に書かない（k = 1 なら段 1 と同じ設定になる）。
- 回し手（`--k`・`--interval-choices`）は、k と選択肢を `meta.json` の `k`・`state_poll_interval_choices_s` に残す。保存先の道のりには入らないので、値を変えるときは `--stage` を変える。集計は `runs.csv` の最後の 2 列に出す（記録の無い段 1 の run では空）。
- 集計の `decisions.csv` には、段 2 のエージェントが書いた `state_poll` の行があるときだけ、`action_prob` と `consecutive_poll_timeouts`（中央値と四分位）、`last_poll_status=<値>` の頻度（`null`・`answered`・`timed_out`・`pending` の順）を足す。pilot2 を元のコードと集計し直して比べ、`runs.csv` 以外の CSV と PNG の図がバイト単位で同じ、PDF の図は `CreationDate` を除いて同じ、`runs.csv` は足した 2 列（空）を除いて同じことを確かめた。

### 報酬の材料（2026-10-26 決定）
- 報酬は「遅れ」と「制御の通信量」の重みづけで組む。遅れには、ホップ数が多いほど重い重みを掛ける。
- ホップ数の重みは集計の側で掛ける。エージェントは判断の時点でホップ数を知らない（判断の状態にあるのは origin ごとの進み具合と隣の通知だけ）が、集計はトポロジーを知っている。報酬の式そのものと重みの値は、学ぶ段で決めればよい。この effort では、どの式にも使える材料（レコードとノードの組ごとの遅れ、ホップ数、通信量）を残す。
- 名前の重要度による重みは、この effort では入れない。重要度の定義がまだ無く、取得は (origin, seq) で送るのでレコードの属性は届くまで分からず、方針の入力にするにはプロトコルの変更が要るため。

### 負荷（2026-10-26 決定）
- origin は段 1 と同じ h0 と h4 の 2 つのまま、1 回の生成で k 件のレコードを作る。段 1 では 1 度に取る件数がほとんど 1 件で、取得の計画に幅が無かったため。
- エージェントは時刻が来た予定をまとめて全部レコードにする（`agent.py` の `_drain_schedule`）ので、生成器が同じ `at_s` の予定を k 件並べればよく、エージェントの変更は要らない。
- origin を 9 つ以上に増やす案は採らない。判断の状態に載る origin は最大 8 つで、超えると `truncated` になって状態の一部が記録から落ちる。
- 負荷が段 1 と違うので、段 1 の数字とは直接比べない。同じ負荷で、既定の方針（間隔 2 秒 ± 20%）の基準も回す。

### 段 1 のデータで数えたこと（2026-10-26）
- 段 1 のチケット 06 の Resolution に書いた 2 つの推測を、s1 の 500 回で数えた。表と定義は `evidence/s1-breakdown/`。
- 切断で増える遅れの 90〜94% は、上流がレコードを持っているのにリンクが落ちていた時間で、状態確認の間隔では縮められない。状態確認の待ちは、1 ホストあたり平均 1038 ms（p = 0）から 1059 ms（p = 0.4）でほとんど変わらない。リンクが戻ったあとの待ちは、ふだんの待ちと置き換わるだけ。
- それでも、状態確認の間隔は遅れのうち方針で動かせるほぼ唯一の部分。p = 0 では遅れの 99%、p = 0.4 でも 26% が状態確認の待ちで、平均はおよそ間隔の半分。間隔を縮めれば、この部分はどの p でも同じように縮むと見ている。
- 通信量が p とともに減るのは、リンクが落ちている間に送った状態確認に返事が来ないため。取得の回数はどの p でも同じで、減るのは取得の判断の数（1 回の判断でまとめて取る）。p = 0 の通信量は、グループ名が 2 文字短いぶんおよそ 47 B／レコード少なく出ている。
- 間隔の効きが p によらないなら、状態によって間隔を変える方針は、決まった間隔に勝ちにくい。そのときは学ぶ段の方向として、ベイズ最適化で間隔を決めれば足りるかもしれない。状態に応じて変える価値がありそうなのは、返事の来なかった状態確認のあと（「判断の状態に足すもの」）。

## Fog

- 間隔の選択肢の値と数。短い試走で、遅れと通信量がどれだけ動くかを見て決める。
- k の値。短い試走で、1 度に取る件数の分布がどう広がるかを見て決める。
- 切断率をいくつ回すか、条件ごとの seed の数、run の長さ。段 1 は 5 条件 × 100 seed で約 22 時間だった。
- リンクが戻ったあとの状態確認の待ちが、ふだんの待ちより長い理由（p = 0.1〜0.4 で 39〜132 ms）。
- 状態確認の間隔のゆらぎをやめることの影響。段 1 のゆらぎには、ノードどうしの状態確認が同じ時刻にそろうのを防ぐ役目もあった。離散の選択肢を判断ごとに選び直すなら、そろい続けることはないと見ているが、試走で確かめる。
- 報酬の材料として、判断ごとに何を結びつけるか（判断のあと何秒の遅れと通信量か）。学ぶ段の方向で必要なものが違うので、どの方向にも使える粒度で残す方法を決める。

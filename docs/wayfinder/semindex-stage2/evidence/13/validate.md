The A1 and A2 failures are dominated by millisecond-resolution coincidences rather than rule errors -- but see the unmodelled effects below for what that claim does NOT cover. The A3 failure is not of that kind: s6wait p0.6 misses a cell aggregate, which is the layer Q61 actually reads, and it misses it on the boundary spec.md fixes. What saves the Mode B answer is that Mode B is scored against the measured cell's own bootstrap interval and passes every line here, including in that cell.

- **A1.** The 3 failing cells (s6short p0.4 (98.463 %), s6short p0.6 (98.705 %), s6wait p0.6 (98.962 %)) each contain one or two runs where a poll was sent inside the few-ms window in which a link is flipping. The events.jsonl stamps are whole milliseconds, so which side of the flip that poll fell on is not recoverable (facts-reply-fetch.md §4 and its own UNCONFIRMED 3 say the same). In a **policy** stage one such coin flip is not local: the outcome decides the next interval, and the extra or missing poll shifts that node's shared jitter stream by one draw for the rest of the run, so every later poll of that node diverges. The same coin flip costs nothing in the non-policy arms, which is why only short/wait cells fail A1.
- **A2.** A record created or stored at the holder in the same millisecond as a reply is served is on one side of the serve instant or the other, and the log cannot say which. Each such flip moves a 4-record batch by one whole poll interval at the node that missed it, and the shift then propagates down the line. The rate therefore tracks the poll interval: the 0.5 s arm (s5b0p5 / s6b0p5) sits at 97.0-98.3 % while the 10.043 s arm sits at 98.9-100.0 %. The shorter the interval the more replies there are to collide with, and one missed batch is already a 500 ms shift, well over the 150 ms tolerance. The cells that fail both A1 and A2 (s6short p0.4, s6wait p0.6, s6short p0.6) fail A2 for the A1 reason above, not this one. The fetch layer itself is not implicated: wherever the advertisement agrees, the store time agrees to a few ms.

### Effects seen in the logs and deliberately NOT modelled

- **Slow replies.** The model gives every poll a 1 ms RTT (spec.md). In the logs 65 of 315 315 in-run replies (0.021 %) arrive more than 100 ms after their poll: p50 422 ms, max 1040 ms. Worked example: s5wait p0.4 seed 2, h2 polls h1 at t0+65 208 ms with the link up since t0+65 000 ms, and the reply lands at t0+66 020 ms -- 812 ms. Only 12 of the 58 such polls that follow a `link_up` are within 1 s of it, so this is not purely interface recovery; plain agent-loop stalls account for the rest. It is left out because fitting it would need a new constant, which spec.md forbids. At 0.021 % of replies it cannot be the main A2 driver, but it is not a millisecond tie either.
- **Unexplained asymmetry.** Over 100 runs of 5 cells, where the simulated and the logged `state_rx` hi maps disagree at the same instant, the simulation is BEHIND the log 664 times and AHEAD 344 times. A pure rounding tie should be symmetric, and pushing the serve instant one millisecond later (the delta sweep's next candidate) made the total worse, not better. The cause is not established.
- **`extra` / `truncated`.** Implemented, never exercised: 0 of 137 659 logged advertisements carried a non-empty `extra` (facts-reply-fetch.md §1), so this replay cannot be said to have tested that path.
- **`clamped` reschedules and `state_poll_late_reply`.** Both implemented, both zero in every logged run and in every simulated run (facts-timers.md §9).

The split boundary scores better on all three lines, and §4's start/completion reading is a real argument for it. It is still tuned: it was found by scoring A1 after the first full run, and §4's own best mapping -- the one spec.md line 15 names -- is `actual_at` for both. Reproduce either row with `LINK_UP_FROM_ISO_TS=1 python3 replay.py` / `python3 replay.py`.

The serve-instant tie rule (model fix 1) is the second tuned choice: the three candidate offsets were scored against the logs on a 12-run set and the best was kept (A2 96.8 / 98.5 / 98.0 % for serve-before-send-ms / between / after-receive-ms). What the model kept -- holder events stamped at the send millisecond are IN -- is also **not** what the source says for `record_created`: `Agent.step` runs `transport.poll()`, which serves every Interest, and only then reads `now = transport.now()` and calls `_drain_schedule(now)` (agent.py:1071-1077), which stamps each new record `round(now * 1000)` (agent.py:861-872). A `record_created` stamped at millisecond X was therefore created from a clock read AFTER the serve of that iteration, so it cannot be in a reply whose Interest was sent at X: for `record_created` the source decides the tie the other way. `record_stored` is written from inside `poll()` itself and stays genuinely ambiguous. `review-rules/alt_rule.py` implements the source-faithful split; it was not adopted, because adopting it after seeing its score would be the same tuning again.

No constant was changed after seeing a result. The constants at the top of `replay.py` are the ones spec.md fixes, plus `RETRY_LAG_MS = 2.0`, which facts-reply-fetch.md §6 measures directly (a backed-off retry is re-planned +1..2 ms after `next_attempt_at`, not +[0,100] ms, because the wait is a whole number of tick periods).

## Deviations from spec.md

1. **`agent_start.ts_ms` is treated as exogenous**, in both modes, alongside `t0_ms`. spec.md's exogenous list does not name it. It is process-launch timing, not a timer rule: facts-timers.md §3 shows the first poll lands 8-103 ms after `agent_start` (one `receive_timeout_ms`) but 434-2187 ms after `t0_ms`, dominated by process launch. Without it the first poll of every node would be unplaceable to better than ~1.7 s. Mode A then takes the first poll's lag from the log like any other; Mode B draws it U[0, 100] ms, one draw per node shared by both neighbors (facts-timers.md §2: both neighbors share the first tick).
2. **The serve instant is pinned at millisecond granularity** rather than left as a fraction of POLL_RTT (fix 1 above). spec.md fixes POLL_RTT at 1 ms but says nothing about which side of a same-millisecond holder event the serve falls on. The rule was **chosen by score on a 12-run set** (A2 96.8 / 98.5 / 98.0 % for serve-before-send-ms / between / after-receive-ms), so it is **tuned**, and for `record_created` it is also contrary to the source. See *Tuned variants* above for both points.
3. **`RETRY_LAG_MS = 2.0` is an extra constant** not in spec.md's list, forced by facts-reply-fetch.md §6 (see above).
4. **Fetch planning also runs on every record_stored and every fetch_timeout**, not only on `state_rx`. spec.md names only the `state_rx -> fetch_plan` 0 ms edge. `transport.poll()` returns on any packet and `on_tick` then runs `_send_fetch_plan` for every neighbor, which is why a length-8 plan is followed by the next plan on the same pair after 1-3 ms in the logs (measured over 4 runs, p50 2 ms). Without it a backlog larger than the in-flight window of 8 would drain one window per 100 ms.
5. **A1's denominator is every poll of the run**, not only in-window polls, and unpaired polls (one side has more) count as mismatches. spec.md does not say. A1's outcome label comes from the same reply-attribution rule the metrics use.
6. **B2 for `polls timed out` is reported but not gated.** spec.md's B2 line names delay, polls_sent, bytes and cens4 only.
7. **~~`link_up` uses the `results.json` ISO `ts`~~ -- withdrawn 2026-11-17.** Both link directions are back on `t0 + actual_at*1000`, which is what spec.md line 15 instructs. No deviation from the spec remains on the link boundary; the ISO-`ts` variant is reported under *Tuned variants*.
8. **A policy stage's provisional send-time timer is queued at the bare due instant and its tick lag is drawn only if the timer is still live** (`ev_poll_due`), while the non-policy path draws the lag at send time. spec.md says nothing about RNG stream order. Drawing at send in the policy path too would consume one extra Mode B `sim_rng` value per poll and shift every later draw of the run, which would move the 14 existing policy cells although their schedule is unchanged. The deferred draw is what makes `validate_cells.csv` byte-identical across model fix 6.
9. **A fact file was corrected while scoring this replay**, and the measured side here follows the corrected version: facts-metrics.md said `ngap - nnorep` differs from the `state_rx` count in "5 of the 42 cells". It differs in **7**. This replay's own cross-check compares both quantities for every cell and reports no difference, so nothing in the numbers above moves.

### Jitter: regenerated, not read back (spec.md line 24 asks which and why)

Both modes re-seed the stdlib streams -- `random.Random(f"state_poll_interval_jitter:{seed}:{node}")` and, for the choices arms, `random.Random(f"state_poll_interval:{seed}:{node}")` -- one draw per `state_poll`, consumed in send order across both neighbors of a node, and none per reschedule (a reschedule reuses the poll's own `jitter_u`). `applied_interval_s` is not read back, for three reasons: s5wait/s6wait row 1 has `jitter_frac = 0`, so the draw is unrecoverable from it although it still advances the stream (facts-timers.md §4b); Mode B and any changed rule produce polls the log has no row for; and regenerating is what makes Mode A a test of the rule rather than a replay of its own output. facts-timers.md §4b confirms the streams reproduce the logged values exactly.

### Reproducibility

- Mode B replicate RNG: `random.Random(int.from_bytes(sha256(f"{stage}:{p}:{seed}:{rep}").digest()[:8]))` -- not Python's salted `hash()`, so the 16 worker processes draw the same streams on every run.
- Bootstrap: `numpy.random.default_rng(20261117)` instantiated once per cell, so every metric of a cell is resampled on the same 2000 x n_seeds index matrix.
- 16 worker processes on a 6-core host (deliberately oversubscribed, as the task specified); wall clock 23 s for all 840 runs x (1 Mode A + 5 Mode B replicates).

# evidence/13: 「空が続くあいだ間隔を延ばす」決まりを、今ある run の上でなぞり直す（2026-11-17）

evidence/11 と 12 で測らずに残した問い「空の答えが続くあいだ状態確認の間隔を延ばす決まり（Trickle、RFC 6206 の形）にすると、状態確認の数と遅れはどう動くか」に、新しい run を回さずに答える。
今ある 840 本のログから、5 台のエージェントの動きを机の上でなぞり直す台本（`replay.py`）を作り、まず今の決まりをなぞってログと合うかを確かめ、合った範囲だけを使って新しい決まりを回した。

**ここの数字は全部なぞり直しの値で、実機で測った値ではない。** 実測と照らしたのは今ある 6 つの決まりまでで、新しい決まりの値を実測と照らしたものは無い。

## 先に結論

- なぞり直しは、**出来事ごとにはログと合わない**（先に書いた合格の線で不合格）。**マスの集計では合う**（遅れ・打ち切り・状態確認の数・バイトが、実測の 95 % 区間に入る）。決まりだけを別の腕のものに入れ替えても、その腕の実測に合う。
- 試した 5 通りのうち 3 通りは、7 マス全部で、状態確認の数が同じ固定の間隔より遅い。1 通りは 7 マス中 6 マスで遅い。
- 残る 1 通り（最短 3.695 秒）は、切断の無いマスでだけ 18 % 速い。切断のあるマスでは、0 と見分けられないか、遅い。
- 測れたのは、間隔が不ぞろいになっていること。そのせいで遅いというのは推し（「測ったもの、推したもの」の節）。

## なぞり直しの作り

外から与えるもの（run から取り、なぞり直さない）は、切断の時刻表、origin がレコードを作った時刻、エージェントが動き始めた時刻、決まりの設定。
なぞり直すものは、5 台ぶんの状態確認（送る時刻、答えが届くか、答えの中身）、取得（計画、同時 8 本まで、時間切れ、2・4・8・16 秒の再試行）、レコードを保存した時刻。

決まりはソースから読んで、ログで照らしてある。読み取りの記録は `facts/`（3 本、英語。台本の名前が出てくるが、その台本はこのディレクトリには置いていない）。

- 送る時刻（`facts/timers.md`）: 14 ステージ 786553 件の状態確認で、式とのずれは 0〜100 ms（エージェントが時計を見る周期）。間隔の揺らぎの乱数は seed とノード名から作り直せる。
- 答えの届き方と中身（`facts/reply-fetch.md`）: 切断の時刻表だけから答えの有無を当てると 21573 件中 21564 件。隣のログだけから答えの `hi` を当てると 16815 件中、同じ時刻で 16643 件、前後 4 ms を許すと 16810 件。レコードは、状態確認の答えの後の取得でしか届かない（40252 件で例外なし）。
- バイトと遅れの定義（`facts/metrics.md`）: evidence/09〜11 と同じ。遅れは 4 ホップ先に保存されるまでの時間の、打ち切りを除いた平均。

回し方は二つある。

- A（位相を借りる）: エージェントが時計を見る位相を、状態確認ごとにログから借りる。決まりの写し間違いを出来事ごとに見つけるための回し方。
- B（位相も引く）: 位相を 0〜100 ms の一様乱数で引く。1 本につき 5 回。決まりを替えるときはログに位相が無いので、この回し方しか使えない。

### 結果を見た後に足した測り（`after.py`、`after.md`。`spec2.md` には無い）

**1. 線の引き方の偏り。** 「得」は 4 点を結んだ折れ線に対する値で、固定の間隔の本当の曲線が下に膨らんでいると、点と点の真ん中に落ちる決まりは得が大きめに出る。T37 の正の得は 3 つとも真ん中にある。倍率 1 で最短と上限を同じにした決まりは固定の腕と同じ出来事を出す（下の恒等の確かめ）ので、T37 の状態確認の数をはさむ固定の間隔を 5 つずつ足して回し、それと比べ直した。

| マス | 折れ線に対する得 | 足した固定の腕に対する得 |
|---|---|---|
| `s5` p 0 | +17.8 % | +17.9 % |
| `s5` p 0.2 | +4.5 % | +2.3 % |
| `s6` p 0.2 | +2.4 % | −1.6 % |

切断の無いマスの +18 % は折れ線のせいではない。残る二つは小さくなり、もとの区間も 0 をまたいでいる。`s6` の p 0.2 に足した腕の遅れは間隔の順に並んでいない（6.0 秒で 21048 ms、6.2 秒で 20143 ms）ので、このマスの得は ±5 % ほどより細かくは読めない。
偏りの向きは一つで、負の得は控えめに出ている。レビュー役が固定の腕を 1 つ抜いて残りの 3 つを結んだ線と比べたところ、7 マス中 6 マスで +9〜+16 %、`s5` の p 0 だけ −1.2 %・+1.7 % だった（この計算はレビューのもので、このディレクトリには無い）。

**2. なぜ遅くなるか。** 最初の報告は「データが来るときに間隔がいちばん長くなっている」と書いていたが、測ると合わなかった。

| マス | 決まり | 新しいものが来た答えの直前の間隔 | 空の答えの直前の間隔 | 間隔の平均 | 適当な時刻に当たる間隔 |
|---|---|---|---|---|---|
| `s6` p 0.2 | 固定 3.695 秒 | 3.75 秒 | 3.75 秒 | 3.75 秒 | 3.76 秒 |
| `s6` p 0.2 | T05 | 2.65 秒 | 2.59 秒 | 2.44 秒 | 6.04 秒 |
| `s6` p 0.2 | T136 | 3.90 秒 | 4.33 秒 | 3.90 秒 | 6.63 秒 |
| `s6` p 0.2 | T37 | 5.22 秒 | 7.45 秒 | 5.98 秒 | 7.29 秒 |
| `s5` p 0 | T37 | 4.37 秒 | 8.35 秒 | 5.51 秒 | 6.87 秒 |

「適当な時刻に当たる間隔」は、間隔を長さで重みづけした平均（Σg²/Σg）。レコードがいつ落ちるか分からないとき、長い間隔ほど当たりやすいことを表す。

- 新しいものが来た答えの直前の間隔は、空の答えの直前と同じくらいか、短い（T05 は 2.65 秒と 2.59 秒でほぼ同じ、T136 と T37 は短い）。決まりは、データが流れているあいだ短い間隔でいる。最初の報告の説明は採らない。
- この表は 3 マス（`s6` の p 0.2・0.4、`s5` の p 0）の、5 回のうち 1 回目だけ、20 seed の値。
- 間隔が不ぞろいになっている。T05 は平均 2.44 秒なのに、適当な時刻に当たる間隔は 6.04 秒。固定の腕では二つが同じ。
- 全部そろった後の状態確認は減っている（`s6` の p 0.2 で、T05 は 368 回のうち 61 回、固定 3.695 秒は 256 回のうち 94 回）。減ったぶんより、不ぞろいの損のほうが大きい。

## 測ったもの、推したもの

測った（なぞり直しの上で）: 上の表の数。

推した（測っていない）:

- 遅くなるのは、間隔の不ぞろいのせいだと見ている。この負荷は origin が 2 秒おきに 60 秒間レコードを作り続けるので、空の答えの後すぐに次のレコードが来る。決まりは、空のたびに延ばし、来たら最短に戻すことを繰り返し、短い間隔と長い間隔が混ざる。状態確認の数が同じなら、等間隔がいちばん待ちが短い。Trickle が効くのは変化がまれにまとまって起きるときで、この負荷はそうなっていない。evidence/12 の「空が続いた回数だけでは次の空は当たらない」と同じ向きの結果。
- T37 が切断の無いマスでだけ速いのは、生成のあいだ答えがほとんど毎回新しいものを運ぶので、間隔が 3.695 秒に張りつき、生成の前と後だけ 10 秒に延びるからだと見ている（`s5` の p 0 で、T37 の空の割合は 0.349、固定の腕は 0.51〜0.86）。切断があると、切断明けのまとめ取りの後に空が続き、間隔が延びたところへ次が来る。
- 学習の方針について: この負荷では、固定の間隔を結んだ線がすでに強い。空かどうかを見て間隔を変える決まりは、その線を越えなかった。学習された方針が式を越える余地を見るには、生成の始まりや周期が前もって分からない負荷が要るという見立ては変わらない。

## 確かめたこと

- 実測側の値（遅れ、打ち切り、状態確認の数、答えの数）は、evidence/09・10 の `live_main.csv`・`perrun.csv`、evidence/11・12 の `cells.csv` と、42 マス全部で差なし（`replay.py` が毎回照らし、差があれば止まる）。なぞった側と実測側は同じ採点の関数を通る。
- 恒等の確かめ（`identity.py`、`trickle.py` が毎回先に走らせ、落ちたら止まる）: 倍率 1 で最短と上限を同じにした決まりは、固定の腕と同じ出来事を出す。4 つの間隔、3 seed、A と B で 24 組。ただし倍率 1 では間隔が動かないので、延ばす・上限で止める・時刻を引き直す、の枝はこの確かめを通らない。その枝は、レビュー役が 1 組の（ノード、隣）について別に書いた計算で確かめた（5 通り、2134 件の状態確認で差 0。この計算はこのディレクトリには無い）。
- 2 秒より短い間隔での動き（前の状態確認が解決する前に次を送る）を足しても、今ある 42 マスの値は 1 バイトも変わらなかった。足す前の台本との出来事ごとの突き合わせは作業場所でやったもので、このディレクトリからは作り直せない。
- レビュー: 台本ごとに 2 人ずつ、別の向きから（決まりがソースどおりか、採点と比べ方が正直か）。指摘は全部直すか、この README に書いた。主なもの: 復旧側の境目を結果を見た後で替えていた（元に戻した）、折れ線の注意が当てはまらないマスに付いていた（上の「足した測り」1 で置き換えた）、遅くなる理由が測らずに書かれていた（同 2 で測り直した）、得が 1e-16 の行を正に数えていた（直した）。
- 作り直すと、`validate_cells.csv`、`trickle_cells.csv`、`trickle_gain.csv`、`swap.csv`、`after.md` はバイト単位で同じになる（`RUN.txt`）。

## 読むときの注意

- 新しい決まりの値は、なぞり直しの中だけの値。実機では測っていない。
- T05、T136、T136s、T136c は最短が 2 秒（状態確認の寿命）より短く、切断中に、ログに一度も現れていないソースの枝（前の状態確認が解決する前に次を送る、過去になった時刻の繰り上げ）を通る。この 4 つの値はソースの読みだけに頼っている。T37 はその枝を通らない。
- 「得」は状態確認の数を横軸にした値。バイトを横軸にすると、`short` と `wait` は 2〜7 ポイント良くなる（時間切れの状態確認は答えのぶんのバイトが無いため。レビュー役の計算）。5 通りの決まりは 1.5 ポイント以内しか動かない。
- バイトは、答えの大きさの平均が決まりによらないと置いて出している。
- 7 マスは独立な 7 回の確かめではない。入力は二つの腕の同じ 20 seed で、負荷はどれも同じ（origin ごとに 120 個、2 秒おき、t0+13 秒から）。
- 遅れは打ち切りを除いた平均なので、打ち切りの多い決まりを良く見せる。
- 決まりどうしで共有しているのは、外の入力と、揺らぎの乱数の種まで。時計の位相の乱数は種だけが同じで、決まりごとに引く回数が違うので、値は最初に間隔が変わったところから別になる（位相は最大 100 ms、間隔は 500 ms 以上）。
- なぞり直しに入れていないもの: 遅い答え（ログの答えの 0.021 %、最大 1040 ms）。答えの飛び飛びの持ちぶん（`extra`）と打ち切り（`truncated`）は書いてあるが、ログでもなぞり直しでも一度も起きていない。

## 作り直し方

このディレクトリで、`/home/lab_shared/cefore-semindex/.venv/bin/python3 -B` を使う（`semindex` は import しない。numpy だけ要る）。run の置き場所は環境変数 `STORE`（既定 `/home/lab_shared/semindex-eval`、読むだけ）。

1. `python3 -B replay.py` → `validate_cells.csv`、`validate.md`（23 秒）
2. `python3 -B trickle.py` → `trickle_cells.csv`、`trickle_gain.csv`、`trickle.md`（33 秒。先に `identity.py` を走らせる）
3. `python3 -B swap.py replay.py > swap.csv`（1 分）
4. `python3 -B after.py` → `after.md`（1 分）

1 本の run の出来事を見るには `python3 -B replay.py --trace <stage> <p> <seed> <A|B>`。

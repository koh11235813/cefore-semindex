     PYTHONPATH=$W/src $PY -m semindex.evalagg \

### 3. 打ち切りと、p 0.5・0.6 の [4] の偏り

- 固定 10.043 秒の腕は、p 0.5 で 22.3 %（4800 組のうち 1072 組、20 本のうち 16 本）、p 0.6 で 31.7 %（1520 組、16 本）が打ち切られた。p 0.6 の seed 7 と 12 は、4 ホップの組がすべて打ち切られている。
- 遅れは打ち切られなかった組だけの平均なので、この腕の遅れは低く出ている（どれだけ低いかは測っていない）。方針のバイトの位置で、線の値の 0.75 / 0.68（短縮、p 0.5 / 0.6）と 0.82 / 0.78（5 秒待ち）の重みがこの腕から来る。バイトをそのままにして遅れだけを直すなら、線は上がり、[4] はもっと負になる。
- ただし、打ち切りはバイトの側も動かす。B/レコード・ホップは打ち切られなかったレコード・ホップで割るので、この腕は p 0.5・0.6 でレコード・ホップの 5.7 %・8.3 % を割る数から失い、バイトが高く出ている。バイトも直すとこの腕の点は左に動き、線がどちらに動くかは決まらない。p 0.6 では、この腕の seed の平均から seed 7 と 12 が落ちるが、方針の側には残る。方針自身の打ち切りもある。これらを合わせた偏りの向きと大きさは出していないので、p 0.5・0.6 の [4] は、短縮も含めて割り引いて読む。
- 5 秒待ちは、自分も 7.58 %・5.42 % 打ち切られ（レコード・ホップでは 1.9 %・1.4 %）、CI も 0 をまたぐので、p 0.5・0.6 の 5 秒待ちが線より速いか遅いかは言えない。
- 5 秒待ちの打ち切りが p 0.5 で p 0.6 より多く、短縮（0.33 %）よりずっと多い理由は調べていない（p 0.5 の 11 本に散らばっていて、1 本の外れ値ではない）。

### 5. replay の当てはまり

`evidence/09/` の replay（`replay.py`）を、実測と同じ s6 の切断の予定（seed 1〜20、seed ごとに 10 回）で回し、実測と比べた（replay − 実測、seed の bootstrap の SE）。replay の決まりは、固定の腕が `Fixed(x)`、短縮が `Table((10.043, 3.695))`（失敗の後の待ちにもゆらぎ）、5 秒待ちが `SlotBlind(10.043, 5.0)`（失敗の後の待ちにゆらぎ無し）。

| 決まり | p | 遅れのずれ s6 ms（SE） | 遅れのずれ s5 ms（SE） |
|---|---|---|---|
| 短縮 | 0.2 | −163（575） | −1048（616） |
| 短縮 | 0.4 | −503（901） | +1051（551） |
| 5 秒待ち | 0.2 | −311（824） | −574（520） |
| 5 秒待ち | 0.4 | −1016（1405） | −323（815） |

- 遅れと無駄は、5 秒の枠のときと同じくらい合う。ずれは点の値で 3.7 % 以下で、どれも有意ではない。ただ、方針の遅れの SE は 0.6〜1.4 秒あり、p 0.4 で 2〜3 秒のずれは否定できない。
- 固定の腕の遅れのずれは、p 0.6 の 0.5 秒の腕（+400 ms、2.7 SE）を除いて 2 SE 以内。replay は 0.5 秒の腕の状態確認を 1.3〜3.6 % 少なく数える（ループの遅れの `0.035·p` の項。`evidence/09/` の 5. と同じ）。p 0.5 の 10.043 秒の腕は、replay の遅れが実測より 3.7 秒長い（1.9 SE）。実測の側の打ち切りの偏り（3.）と同じ向き。
- p 0.5・0.6 は replay の返事のバイトが無いので、遅れ・無駄・状態確認の数だけを比べた。全部の表は `replay.md`。

### 6. 失敗の後の待ちの選び直し（replay）

計算の前に決めた手順（PLAN、2026-11-12）で選び直した。答えの後は 10.043 秒のまま、失敗の後の待ち w だけを変える。決まりの形は 3 つ（短縮の形 `Table((10.043, w))`、5 秒待ちの形 `SlotBlind(10.043, w)`、2 段の待ち `Table((10.043, w1, w2))`）、w は 0.5〜12 秒。生成した seed 21〜120 の予定（学習）で [4] が最小のものを選び、実測と同じ seed 1〜20 の予定（確かめ）で、同じ形の変えない決まり（短縮の形と 2 段は s6short、5 秒待ちの形は s6wait）と比べた。

- 回す条件（Δ[4] が −2 秒より小さく、CI95 が 0 をまたがず、変えない決まりの replay のずれが 2 秒より十分小さい）を満たした形は無い。
- 5 秒待ちの形の p 0.4 だけは、Δ[4] の条件を満たした。ただし次の 3 つで、決めた手順どおり回す前に利用者に聞き、実測では回さないことにした（2026-11-12、利用者の判断）。
  1. バイトを変えない決まり以下に抑えると、学習の seed で s6wait より速い 5 秒待ちの形の候補は無く、Δ遅れは 0。選んだ候補（2.75 秒）はバイトを 2.38 B（15 %）多く使う。[4] はそのバイトの差を線で割り引いた後でも −2.3 秒の得を示すので、二つの比べ方の結論が食い違う。
  2. 変えない 5 秒待ちの replay のずれは −1.0 秒（SE 1.4 秒）。「2 秒より十分小さい」に数を決めていなかったので、計算の後で |ずれ| + 1.96 SE < 2 秒と読み、5 秒待ちの p 0.4 は満たさない（3.77 秒）。この読み方は計算の後で決めたものなので、判定を支えているのは 1. のほう。
  3. 同じ seed の上で s6short と比べると、選び直した 5 秒待ちの形の [4] の得は −0.7 秒しかなく、同じ w 2.75 の短縮の形の得は −35 ms。−2254 ms のうち 1554 ms は、変えない 5 秒待ちと短縮の差（7. の 2.）を埋めたぶん。
- p 0.2 の得は、確かめの seed 1〜20 のほうが学習の seed 21〜120 より大きい（短縮の形 −914 対 −105、2 段 −1435 対 −468、5 秒待ちの形 −983 対 −751。1.3〜8.7 倍）。この 20 本では、変えない二つの決まりの replay の [4] がどちらも学習のときより弱い（短縮 −2644 対 −3843、5 秒待ち −2518 対 −3234）。学習の値は多くの候補（一つの待ちの形で 47、2 段で 576）から選んだ最小値で、得を大きく見せる側に偏るので、学習の値のほうが確かとは言えない。判定には、確かめの seed の差と CI を使う。
- 学習での [4] は最適の近くで平らで、最良から 300 ms 以内の w は、短縮の形が p 0.2 で 1.75〜4.0 秒、p 0.4 で 2.5〜3.0 秒、5 秒待ちの形が 1.75〜3.75 秒と 2.25〜3.0 秒。
- 先を知っている参照の決まり `Oracle(10.043)` の [4] は、確かめの seed で p 0.2 が −5965 ms、p 0.4 が −12241 ms。遅れは s6short より 2.5 秒（p 0.2）と 4.3 秒（p 0.4）短い。この決まりは、10.043 秒先の状態確認が切断の中に落ちるときだけ、リンクが戻った直後に送り直す。失敗には反応せず、リンクが戻るたびに送るわけでもなく、失敗もしうるので、どの決まりも届かない限りではない。

### 7. 前もって決めた読み方

1. 「二つの決まりがどちらも固定の腕の線より下に留まり、選び直した決まりの得が小さい」: 形をまたいだ比べのある p 0.2・0.4 で成り立つ。実測では、どちらも p 0.2・0.4 で線より下（p 0.5・0.6 は、短縮も線より下だが、3. のとおり線の偏りが決まらず、5 秒待ちは言えない）。replay でも、変えない二つの決まりは p 0.2・0.4 で線より下（短縮 −2644 / −5731 ms、5 秒待ち −2518 / −4177 ms、CI はすべて 0 より下）。選び直した得は p 0.2 でどの形も 2 秒に届かない（学習の seed で −0.1〜−0.75 秒）。map の読み方では、「失敗に反応する」だけで足りていて、このテストベッドで学ぶことが要るという主張は弱い。
2. 「5 秒待ちだけが得を失う」: 成り立たない。5 秒待ちは得を失っていない（p 0.2・0.4 で CI が 0 より下）し、p 0.4 では短縮も得を減らした。別に見えたこととして、p 0.4 で 5 秒待ちは短縮より大きく得を減らした（実測で s5 の −9.2 秒から −3.9 秒に、短縮は −9.9 秒から −6.1 秒に。replay では 5 秒待ち − 短縮が [4] で +1554 ms、CI 785〜2494）。p 0.2 では差が無い（replay で +127 ms、CI −566〜771）。この差が 5 秒の格子に乗っていたことから来ているというのは、確かめていない見立てにとどまる。この形は長さと格子と裾を一度に変えるので、どれのせいかは分けられない（map に書いたとおり）。
3. 「選び直した決まりが p 0.2 で 2 秒ほどより大きく得をする」: 成り立たない。形を学ぶことの証拠は、この比べからは出ていない。

## 測ったもの、推したもの

- 測った: 遅れ、打ち切り、バイト、状態確認と返事の数、無駄、実測の [4] と線の値、やり直しが切れているリンクに送られた割合、同じ切断の中だった割合、時間切れの割合、切断の予定の一致。
- replay のモデルの値: 同じ切断の予定での予測、replay の [4]、選び直した待ちとその得、参照の決まり `Oracle` の値。
- 推した: p 0.4 で速い腕と 10.043 秒の腕が速くなり、10.043 秒の腕の打ち切りが減った理由（5 秒の枠の長い裾が無くなったこと）。
- 分かっていない: p 0.4 で方針が遅くなった仕組み、p 0.5・0.6 の [4] の偏りの向きと大きさ、5 秒待ちが p 0.4 で短縮より大きく得を減らした理由（格子のせいかどうか）、5 秒待ちの p 0.5 の打ち切りが多い理由。

- p 0.2・0.4 の `perrun.csv` の 240 行と、主な表と [4] の値は、2026-11-11 に p 0.2・0.4 がそろった時点で別に作った途中の表（`evidence/09/perrun.py` を p で絞った写しと、`ana.py` の関数を呼ぶ別の台本）とバイト単位で同じ。
- `recheck.py`（`recheck.txt`）は、解析の台本とは別に書いた 3 つの数え直し。

  2. やり直しを生の `decision` の出来事から別に組み立て、切れていたか、失敗した状態確認と同じ切断の中かを、切断の予定から別に判定した。5 か所は `retry_table.csv` と一致し、7 か所は 20 本でやり直しが 1〜4 本多い（全体の 491〜1980 本のうち）。`retry_table.csv` は `evidence/09/phase.py` の `retries_of` で数えていて、やり直しへの返事が同じミリ秒のうちに届くと、そのやり直し自身の決め直しを直前の決め直しと取り違えて数えない（s5short p 0.4 seed 16 の h2→h1 の 1 本で確かめた）。切れていた割合の違いは 0.0014 以下、同じ切断の中の割合の違いは 0.0010 以下で、4. の読みは変わらない。`evidence/09/` の位相の数字にも同じ数え方が入っている。
  3. `replay.simulate` を直接呼んで、5 秒待ちの形の p 0.4 の確かめの遅れ（34337.4 ms と 29799.6 ms、差 −4537.9 ms）が `replay_retune.csv` と一致した。seed ごとの値も `replay_calib_perseed.csv` と一致した。

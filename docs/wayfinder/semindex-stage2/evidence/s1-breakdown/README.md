# 段 1（s1）の遅れと通信量の内訳

段 1 のチケット 06 の Resolution に書いた 2 つの推測を、s1 の 500 回の生データで数えた結果（2026-10-26）。

1. 切断があるときの遅れの大半は、リンクが戻ってから次の状態確認が来るまでの待ち。
2. 制御の送信量が p とともに減るのは、状態確認の返事と取得が減るから。

## 結論

- **推測 1 は外れ。** p = 0 からの遅れの増え方の 90〜94% は、上流のノードがレコードを持っているのにリンクが落ちていた時間。状態確認の待ち（リンクが戻ったあとの待ちと、切断と関係のないふだんの待ちの合計）は、1 ホストあたり平均 1038 ms（p = 0）から 1059 ms（p = 0.4）までしか増えない。リンクが戻ったあとの待ちは、もともと起きるふだんの待ちと置き換わっているだけで、上乗せになっていない。
- **推測 2 は半分だけ当たり。** 減っているのは状態確認の返事で、取得は減っていない。
  - 返事は 1 回の run あたり 467 回（p = 0）から 273 回（p = 0.4）に減る。リンクが落ちている間に送った状態確認には返事が来ないため。減った割合はおよそ p。
  - 取得の Interest と Data は、どの p でも 1 回の run あたり 240 ずつ（60 件 × 4 ホップ）。半分になるのは `fetch_plan` の**判断の数**で、切断のあとの 1 回の返事で足りないレコードがまとめて分かり、1 回の判断で何件も取りに行くため（判断 1 回あたりの Interest は 1.15 件から 2.29 件）。

## 遅れの内訳（1 ホストあたりの平均、ms）

| p | 合計（平均／中央値） | リンクが落ちていた時間 | リンクが戻ったあとの待ち | ふだんの待ち | 状態確認の往復 | 取得 | p = 0 からの増え方 |
|---|---|---|---|---|---|---|---|
| 0 | 1049 / 1042 | 0 | 0 | 1038 | 3 | 7 | – |
| 0.1 | 1478 / 1197 | 388 | 117 | 927 | 6 | 28 | +429 |
| 0.2 | 2053 / 1354 | 924 | 248 | 798 | 9 | 54 | +1004 |
| 0.3 | 2916 / 1551 | 1744 | 386 | 663 | 14 | 86 | +1867 |
| 0.4 | 4061 / 1828 | 2830 | 502 | 557 | 21 | 128 | +3012 |

ほかに「切断の前にリンクがつながっていたが、状態確認が届かなかった時間」が 12〜23 ms ある。どの成分も 0 以上で、すべての成分の和は、どの組でも合計と 2 ms 以内で一致する。中央値は一般に足し合わせられないので、和が合計になるのは平均だけ。

- 区切り方（2026-10-26 修正: リンクが戻った記録は切り替えの数 ms あとに付くので、P の時点でまだ落ちていると読める組がある。待ちの成分には、リンクがつながっていた時間だけを入れる）: (レコード, ノード) の組ごとに、上流のノード（`record_stored.holder`）が保存した時刻 U から、このノードが保存した時刻 S までを 1 ホストの遅れとする。この区間は直線に沿ってそのままつながるので、和が端から端までの遅れになる。U から、そのレコードが入っている返事のもとになった状態確認を送った時刻 P までを「待ち」とし、その間にリンクが落ちていた時間を「リンクが落ちていた時間」、最後にリンクが戻った時刻から P までを「リンクが戻ったあとの待ち」とする。
- リンクが戻ったあとの待ちは、p = 0.4 で 1 ホストあたり平均 502 ms（遅れの 12% ほど）ある。リンクが戻った瞬間に状態確認を送れれば消える量だが、エージェントはリンクが戻ったことを直接は知らない。返事の来なかった状態確認の履歴を使ってどれだけ減らせるかは、まだ数えていない（段 2 で確かめる）。
- リンクが戻ったあとの待ち（0 でない組だけの平均）は、p = 0.1〜0.4 で 1087・1131・1151・1156 ms。同じ p のふだんの待ち（0 でない組だけの平均）より 39・91・129・132 ms 長い。理由は分かっていない。リンクのイベントの時刻の遅れは 10 ms ほどなので、時計のずれでは説明できない。

## 通信量の内訳（レコード 1 件あたり、バイト）

| p | 状態確認（回数） | その返事（回数） | 取得の Interest（回数） | 取得の Data（回数） | 組み立てた合計／記録された合計 |
|---|---|---|---|---|---|
| 0 | 372.9（467.0） | 1038.5（467.0） | 150.5（240） | 1001.1（240） | 2563.0 / 2563.0 |
| 0.1 | 386.6（464.7） | 942.8（419.3） | 158.5（240） | 1009.1（240） | 2497.0 / 2497.0 |
| 0.2 | 384.6（462.2） | 826.4（369.6） | 158.5（240） | 1009.1（240） | 2378.7 / 2378.7 |
| 0.3 | 382.9（460.3） | 713.0（320.6） | 158.6（240） | 1009.1（240） | 2263.6 / 2263.8 |
| 0.4 | 381.6（458.6） | 599.7（272.7） | 158.5（240） | 1008.8（240） | 2148.6 / 2148.7 |

- エージェントは種類ごとの通信量を記録していない（`counters` にあるのは合計だけ）。種類ごとの値は、名前の形、`holder_state.encode`、`schema.canonical_bytes` から組み立て直した。組み立てた合計は、どの p でも記録された合計と 0.01% 以内で一致する。
- p = 0 の名前は 2 バイト短い。グループ名が `s1_p0_seedN` で、p > 0 の `s1_p0.1_seedN` などより 2 文字少ないため。そのぶん p = 0 の通信量はおよそ 47 B／レコード少なく出ている。そろえると p = 0 はおよそ 2610 B で、p = 0.4 までの減りおよそ 460 B のうち 454 B が返事、7 B が状態確認で、取得は変わらない。段 1 のチケット 06 の表の値（2.56 KB など）は、この差を含んだまま。

## 注意

- 1097 組では、状態確認を送ったのが上流の保存の数 ms 前で、返事は保存のあとだった。この組では P を U にそろえた。
- 90 組では、レコードの seq が返事の `hi` ではなく、記録されていない `extra` にだけあった。この組では、そのレコードを最初に取りに行った判断の直前の返事を使った。
- リンクの時刻は ReCefore の `results.json` の値で、切り替えたあとに付くので実際より中央値で 9.5 ms 遅い。

## 作り直し方

`breakdown.py` は出力をスクリプトと同じディレクトリに書く（`deliveries.csv` は 14 MB）。リポジトリの外にコピーしてから実行する。

```
cp breakdown.py summarize.py <作業ディレクトリ>/ && cd <作業ディレクトリ>
PYTHONPATH=/home/lab_shared/cefore-semindex/src /home/lab_shared/cefore-semindex/.venv/bin/python3 breakdown.py
/home/lab_shared/cefore-semindex/.venv/bin/python3 summarize.py
```

`summary_h1.csv`（遅れ）と `summary_h2.csv`（通信量）がこのディレクトリの表のもと。

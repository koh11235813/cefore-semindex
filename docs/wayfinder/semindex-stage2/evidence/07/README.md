## わかったこと

### 1. fsync をやめると、遅れは短くなり、通信量はほぼ変わらなかった（`summary_cmp.md`・`tables.md`・`commit_time.txt`・`fetchsplit.txt`・`indep_check.txt`）

測ったこと:

- 30 の区画（6 段 × 5 つの p）のすべてで、発見の遅れの中央値は 8〜57%、全ノード一致の中央値は 6〜59% 短くなった。
- 制御の通信量／レコードは、ほとんどの区画で ±1% 以内。外れは 10.043 秒・p = 0.4 の +5% だけ（中央値 1219 → 1274 B）。この指標の分母は作ったレコードの数（この区画はどの run も 240 件）なので、窓の中の制御の送信量そのものが増えている（run ごとの `control_bytes_sent_window_total` の中央値 292,649 → 305,863 B、evalagg の `runs.csv` から。`runs.csv` はここに置いていない）。この区画は打ち切られた組の割合も 9.84% から 3.92% に下がっていて、窓の中で届いたレコードが増えたぶん、取得と返事の通信も増えたと見ているが、確かめていない。
- B の 4 つの腕の発見の遅れの順（短い間隔ほど早い）は、どの p でも変わらなかった。
- 受け取った 1 件を処理する区間（`evidence/05/` の 4. と同じ数え方）は、`s4b0p5`・`s4b10p043`・`s4a` の 383,705 件で中央値 0 ms、p99 1 ms。
- B の取得の平均は、p = 0 で 88〜890 ms だったものが 2〜5 ms、p をすべて含めると 88〜2763 ms だったものが 2〜24 ms になった（`evidence/05/tables.md` と `tables.md` の T3a の b fetch）。
- A の p = 0 の空き待ちの平均は 3 ms（`fetchsplit.txt`）。A の p = 0 の h2・h3 の取得の計画（seed 1〜40）の 9.6% は、いまも上限の 8 件ちょうど（`indep_check.txt` の (c)）。上限には当たっているが、1 件の処理がほぼ 0 ms なので、空いて待つ時間が短い。

推定していること:

- 短くなる割合は、おおむね p が大きいほど大きい（C で 8% → 32%、A で 12% → 22%）。切断のあとの取り戻しでまとめて届くレコードが、1 件ごとの処理の時間を払わなくなったためと見ているが、確かめていない。

### 2. p = 0 では、A の判断ごとの値から B を見積もれるようになった（`tables.md` の T3b）

4 ホップ先の平均の遅れの、A からの見積もりと B の実測（ホップごとの平均の和）の差は、p = 0 では 4 つの腕すべてで ±3% 以内で、差は見積もりの標準誤差より小さい（0.5 秒で 1145 ± 37 と 1180 ± 9 ms、1.359 秒で 2924 ± 72 と 2973 ± 54、3.695 秒で 7625 ± 104 と 7550 ± 159、10.043 秒で 20438 ± 201 と 20578 ± 663）。`evidence/05/` では同じ比べが +202%・+57%・+8%・−11% だった。

外れが消えた仕組みは 2 段ある。

- 1 回の返事で知るレコードの数は、いまも A のほうが多い（0.5 秒の腕で A 15.4 件、B 4.0 件、T3a の batch）。A では上流の隣も自分の上流への間隔を混ぜて選ぶので、レコードがまとまって届くという `evidence/05/` の 2. の仕組みは、NORMAL でも残っている。
- まとまりの大きさが、もう時間に効かない。受け取った 1 件の処理がほぼ 0 ms なので、15 件のまとまりでも取得は数 ms で終わる（0.5 秒の腕の p = 0 で A 4 ms、B 2 ms）。

つまり、ノードどうしが取得の時間を通じてつながっていた部分は消え、まとまり方の違いそのものは残っている。

### 3. p > 0 では、短い腕の外れが残る（`tables.md` の T3a・T3b）

- 4 ホップ先の見積もりの誤差（B の実測との比べ）は、0.5 秒で +49〜+92%、1.359 秒で +26〜+43%、3.695 秒で +4〜+38%、10.043 秒で −3〜−9%。
- 受け持ちのあいだにたまる待ち（in-gap）は −3〜+5%、状態確認のバイト数／レコード・ホップは −10〜+6% で、ずれは小さい。
- ずれはほぼすべて、返事のあとの部分（post）にある。たとえば 0.5 秒・p = 0.2 で、待ちの差 952 ms（A 1976、B 1024）のうち、post の差が 960 ms（A 1685、B 725）。
- 印が付くのは 10.043 秒・p = 0.4 だけ（B の 4 ホップ先の組の打ち切りが 7.00%）。A の p = 0.4 の 4 ホップ先の打ち切りは 1.95% で、印の線の 2% のすぐ下にあるので、p = 0.4 の区画はどの腕もきわどい。

### 4. 判断 1 回ごとの値は B に移らず、続く判断を合わせた値は、データで決まる腕では移る（`seq_model.md`・`seq_vs_B.csv`・`seq_pieces.csv`・`contcheck.txt`）

3. の post は、受け持ちの終わり（次の状態確認）から知るまでの時間で、p > 0 では主に、次の状態確認が返事を得られなかったあとに続く状態確認を待つ時間になる。その長さは続く判断の腕で決まる。そこで、A のデータから B を見積もる方法を 4 つ並べた（定義は `seq_model.py` の docstring）。

- `current`: `evidence/05/` の決まり（待ちのすべてを、レコードが届いた受け持ちの判断に割り当てる）。
- `seg`: 時間の区間ごとに、その区間を受け持つ判断に割り当て直す（失敗した状態確認の受け持ちの時間は、その状態確認の判断へ）。判断 1 回ごとの報酬の形。
- `chain`: A で測った部品（受け持ちの中の待ち、次の状態確認が失敗する割合、失敗のあとに続けて失敗する割合、失敗のあとのあいだ、返事のあとの遅れ）を、全ノードがいつも x の予定に組み立てる。続く判断を合わせる形。続けて失敗する割合を、何回目の失敗かで分ける `chain_step` と、経った時間で分ける `chain_elapsed` の 2 つ。
- `is`: 失敗した状態確認がすべて x を選んでいた A のレコード・ホップだけを残し、重みを掛ける（重要度で重み付け）。

4 ホップ先、p > 0 の、B の実測に対する誤差（`current` / `seg` / `chain_step`、かっこは `chain_step` の z = 差 ÷ 2 つの標準誤差の合成）:

| 腕 | p = 0.1 | p = 0.2 | p = 0.3 | p = 0.4 |
|---|---|---|---|---|
| 0.5 秒 | +49% / +87% / +4%（z 0.1） | +92% / +110% / +31%（z 0.8） | +55% / +117% / +10%（z 0.4） | +88% / +86% / +24%（z 0.8） |
| 1.359 秒 | +35% / +35% / −4%（z −0.6） | +40% / +49% / −1%（z −0.2） | +43% / +69% / −9%（z −1.0） | +26% / +70% / −10%（z −0.9） |
| 3.695 秒 | +4% / +10% / −1%（z −0.3） | +15% / +19% / −3%（z −0.8） | +27% / +34% / +2%（z 0.3） | +38% / +39% / +2%（z 0.2） |
| 10.043 秒 | −3% / −4% / +3%（z 0.9） | −8% / −9% / +4%（z 0.9） | −9% / −11% / +8%（z 1.5） | −8% / −10% / +14%（z 2.4、印） |

測ったこと:

- `seg` は B を見積もれない。誤差は `current` と同じくらいか、それより大きい。B に入れれば `seg` も `current` も B の値そのものに戻る（`seq_model.md` の 1 行目、相対の差 3.3e-06）ので、割り当ての計算そのものは B の上で正しく働いている。
- `seg` が外れるのは、失敗した状態確認から割り当てられる時間（seg carried、x を選んだ判断の受け持ちに届いたレコード 1 件・1 ホップあたり）が、A では腕によらずほぼ同じで、B では x とともに増えるため。p = 0.2 で、A は 1781・1483・1693・1581 ms、B は 724・772・1054・2181 ms（0.5・1.359・3.695・10.043 秒の順）。
- `chain_step` は、データで決まるところでは B と標準誤差の範囲で重なる。1.359 秒と 3.695 秒はどの p でも |z| ≤ 1.0、10.043 秒は p ≤ 0.2 で z 0.9。`chain_elapsed` は、同じ範囲で |z| が 1 をわずかに超える区画がある（1.359 秒・p = 0.3 で −1.20、3.695 秒・p = 0.2 で −1.22、10.043 秒・p = 0.1 で 1.08。`seq_vs_B.csv` から計算）。
- 0.5 秒は、`chain_step` の誤差が +4〜+31%（`chain_elapsed` は +10〜+31%）で、標準誤差が B の値の 27〜36% ある。A の 0.5 秒の腕のレコード・ホップは p > 0 の各区画で 3026〜3272 で、ほかの腕（7936 以上）よりずっと少なく（`seq_pieces.csv` の `n_recordhops`）、この腕が B と重なるかどうかは、このデータでは判定できない。
- 10.043 秒は、p = 0.1〜0.4 で +3%・+4%・+8%・+14% と、いつも正の向きに外れる。p ≥ 0.3 は、B の 4 ホップ先の組の打ち切り（1.58%・7.00%）で B の実測が短めに出ているのと向きが合う。p = 0.1〜0.2 の正のずれは説明がついていないが、z は 0.9 で、ばらつきの範囲に入る。
- `is` は、短い腕の p > 0 では使えない（0.5 秒で −48〜−80%、1.359 秒で −27〜−74%）。0.5 秒の失敗の続きは 10 秒の切断で 20 回ほどになり、そのすべてが 0.5 秒を選んでいた例が A にほとんど無い（重みの合計は、1 になるはずのところホップ 2〜4 でほぼ 0、p = 0.4 のホップ 4 だけ 4.10。`seq_model.md` の Diagnostics）。
- 1 回の状態確認が返事を得られない割合は、p が同じなら腕によらない。p = 0.2 で、窓の中の状態確認について B も A もどの腕も 0.19〜0.20（`seq_pieces.csv` の `dec_pfail`）。`contcheck.py` で別に数え直すと 0.17〜0.18 で、これは窓の前の状態確認（切断が無い）も数えているためで、窓に限ると同じ値になる。
- 失敗のあとに次の状態確認も失敗する割合は、腕による。p = 0.2 で B は 0.91・0.77・0.39・0.15、A は失敗した状態確認が選んだ腕で分けて 0.91・0.78・0.40・0.19（`contcheck.txt`、`seq_pieces.csv` の `dec_c_after_fail` も同じ）。

まとめ: 判断 1 回ごとの報酬は、`current` と `seg` のどちらの割り当て方でも、p > 0 で A から B に移らなかった。続く判断を合わせた組み立てのうち、何回目の失敗かで続きの割合を分ける `chain_step` は、上の範囲（1.359 秒と 3.695 秒、10.043 秒の p ≤ 0.2）で、B と標準誤差の範囲で重なった（経った時間で分ける `chain_elapsed` は、同じ範囲で |z| 1.2 まで）。0.5 秒はデータが足りず、10.043 秒の p ≥ 0.3 は B の打ち切りで比べが甘い。

### 5. h2 の probe が、h2 のループを止めている（`probe_extract.txt`・`probe_analyze.txt`・`probe_analyze2.txt`・`probe_block.txt`・`slow_steps.txt`）

測ったこと:

- 受け取った 1 件を処理する区間のうち 20 ms 以上は、383,705 件のうち 24 件だけで、すべて h2（`slow_steps.txt`）。そのうち 23 件は、ノードの最初の記録から 24.6 秒、34.7 秒…と 10 秒おきの時刻にあり、h2 の probe の止まり（`probe_discovered` から `probe_retrieved` まで）と重なる（`probe_block=yes`）。残る 1 件（`s4b0p5` p = 0.3 seed 7 の 59 ms、最初の記録から 20.3 秒）は止まりと重ならず、原因は調べていない。checkpoint のような長い止まりは、測れる区間（2 秒未満）では、この 1 件のほかに見えなかった。
- `agent.py` の `_run_probe` は、probe の本体を `fetch_content` で同期して取る。その待ちのあいだ、ほかの Data や Interest は処理される（`cefpyco_transport.py` の `fetch_content`）が、`on_tick`（状態確認、tick で出す取得と再送）は走らない。記録でも、止まりの中に打たれた h2 の記録は `record_stored` 1077・`state_rx` 284・`fetch_plan` 67・`fetch_timeout` 8・`fetch_backoff` 8 で、`state_poll` の判断は 0（`probe_extract.txt`）。
- リンクが落ちていると本体が届かず、chunk の寿命の 2 秒を待つ。失敗した取得の止まりの長さの中央値は 2004〜2014 ms、成功は 326〜360 ms。成功の割合は p = 0 で 97〜100%、p = 0.4 で 28〜34%（`probe_analyze.txt` の Blocks）。
- 止まりが窓（120 秒）に占める割合は、p = 0 で 2.5〜2.8%、p = 0.4 で 12.6〜13.6%。FULL の `s2a` でも 4.1〜13.5% あった（`probe_block.txt`）ので、`evidence/05/` の集計にもこの止まりは入っている。
- 次の状態確認の予定の時刻が止まりの中に来た h2 の状態確認の割合は、`s4c` 8.8%、`s4b0p5` 3.9%、`s4b1p359` 6.9%、`s4b3p695` 8.5%、`s4b10p043` 0.1%、`s4a` 6.6%。分母は、h2 が h1 と h3 に出した状態確認のうち、t_i が窓（t0 + 10 秒〜t0 + 130 秒、evalagg と `evidence/05/` の割り当てと同じ）に入り、次の状態確認が記録されているもの（2 つの隣をまとめる）。そうした状態確認は、予定より平均 1.0〜1.2 秒遅れて出ている（Q3 の due の平均 1006〜1209 ms。`s4b10p043` は 3 回だけで 850 ms）。止まりが終わってからおよそ 100 ms 後に出る（`probe_analyze2.txt` の Tail）。h1 と h3 では、同じ区分でも遅れは 40〜50 ms ほどのまま。h2 については、記録された `applied_interval_s` が、実際に空いた間隔と食い違う。
- 腕と段によって効き方が違う。h2 に入るホップ（ホップ 2）の超過（placebo を引いたもの × 露出の割合）は、各 p をまとめ、打ち切られておらず、そのホップ自身のリンクが決まった区間ずっとつながっていたホップに限った値（0.5 秒で、条件を満たすホップは h0 側 76.9%、h4 側 72.9%。`probe_analyze2.txt` の cond%）で、全ホップへの寄与をそのまま表すものではない。0.5 秒で 36 ms と 112 ms（h0 側と h4 側）で、露出していないホップの平均 303・301 ms のおよそ 12% と 37%。1.359 秒で 23 ms と 34 ms（平均 720・712 ms のおよそ 3% と 5%）、3.695 秒で 70 ms と 87 ms（平均 1961・1854 ms のおよそ 4% と 5%）。1.359 秒と 3.695 秒の h4 側は、2 つの placebo が食い違っていて値が定まらない（NID）。
- 10.043 秒は、止まりの中に予定が来た状態確認の割合が B で 0.1%、A の 10.043 秒の状態確認で 7.8%（`probe_analyze.txt` の Q4b）。
- 4 ホップ先まで窓の中で保存された組に、止まりがどれだけ乗っているか（`probe_analyze2.txt` の Q2、どの段と p でも）: 届いた受け持ちの次の状態確認が止まりで延びた時間（`dAttr`）は平均の遅れの 2.5% 以下、ホップ 2 の区間と止まりの重なりは 6.8% 以下、ホップ 2 と 3 の重なりは 10% 以下。どれも、止まりが遅れに足した時間の上限にはならない。`dAttr` は、届いた受け持ちの次の状態確認だけを見ていて、それが失敗したあとの状態確認が止まりで遅れたぶんを数えない。重なりも、止まりのあとに続く状態確認の時刻のずれを含まない。
- placebo（止まりを 4 秒・6 秒ずらしたもの）で引けないところがある。`s4b10p043` は露出したホップがほぼ無くて定まらず、`s4c` は p によって定まらない区画があり、`s4a` はまとめても標準誤差が大きい。

推定していること:

- 10.043 秒の B で止まりに当たらないのは、全ノードの状態確認と probe が同じ 10 秒の周期でそろっていて、予定の時刻が probe の時刻を避けたまま動かないためと見ている。A では間隔を混ぜるので、そろいが崩れる。確かめていない。

まだ決めていないこと: probe を止まらない形に直して回し直すか、止まりに当たった h2 のあいだに印を付けて外すか、このまま受け入れるか。学ぶ段の方向と合わせて決める。

### 6. `evidence/05/` と行の数が違う出力

- `checks.csv` は 405 行から 330 行、`fetch_by_inflight.csv` は 87 行から 53 行。`checks.csv` は数が 0 の項目を書かないので、`extra` で知ったもの、取得の計画が返事より先だったもの、無効の run などが 0 になった区画の行が無くなった。`fetch_by_inflight.csv` は、判断の時点で取得が残っていた区分（`in_flight_zero` = 0）の行が 41 から 7 に減った。取得が数 ms で終わるので、判断の時点で取得が残っていることがほとんど無いためと見ている。
- `capbind.txt` と `fetchsplit.txt` の `t2k4`・`t2c32k4` の行は、FULL の試走（`evidence/04/`）で、`evidence/05/` のものと同じ。

## 外れた想定

1. NORMAL にすれば、A の判断ごとの値から B を見積もれること。p = 0 では当たったが、p > 0 では短い腕で外れが残った（3.）。
2. 判断 1 回ごとに時間を割り当て直せば、B に移ること（4. の `seg`）。腕ごとの失敗の続き方が A と B で違い、割り当て直しでは埋まらなかった。
3. h2 の状態確認が、記録した間隔どおりに出ていること（5.）。
4. 受け取った 1 件を処理する区間の長い止まりは、fsync を減らしたあとは WAL の checkpoint で出るかもしれないこと。20 ms 以上の 24 件のうち 23 件は probe の止まりで、checkpoint に結びつくものは見えなかった（残る 1 件は調べていない）。

## 確かめていないこと・前提

- 失敗が続く割合が腕によるのは、evalgen の切断が 5 秒の枠ごとにまるごと落ちる形だからと見ている（短い間隔ほど、同じ切断の中で次の状態確認を出す）。続く判断を合わせて扱う必要は、この切断の作り方の性質で、ここで学んだ方針は 5 秒の切断に合わせたものになる。切断の長さや形が違うときに、`chain` の部品がそのまま移るかは確かめていない。
- `chain_step` の 1.359 秒と 3.695 秒の誤差は −10〜+2% で、標準誤差の範囲に入るが、0 と言えるほど狭くはない。
- 1. の、p が大きいほど短くなる理由（取り戻しのまとまり）は推定で、切り分けていない。
- WAL の checkpoint の発生と所要時間は、直接は測っていない。2 秒以上の区間は数え方から外れる。
- 5. の止まりの仕組みは、コードと記録の時刻から読んだもので、止まらない形の probe と比べる実験はしていない。

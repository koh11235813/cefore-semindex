STORE, STAGE, SEEDS and OUT were all left at their defaults (`/home/lab_shared/semindex-eval`, `s11a`,
`1-100`, this directory), so neither output file carries the test banner the two scripts write when any of
the four is overridden.

PYTHONPATH=$W/src comes first because the venv's installed semindex points at another checkout, and both
the evalagg call and perrun.py would import the wrong package without it. `python -I` cannot be used for
the same reason, since it drops PYTHONPATH. Unlike evidence/20's perrun.py, this one puts ../05, ../07 and
../09 on sys.path itself, by absolute path from its own location, so PYTHONPATH carries src alone and the
script runs from any working directory.

perrun.py imports evidence/20's perrun.py (loaded under the name `perrun20`, since this file has the same
basename), through it evidence/09's perrun.py, evidence/05's run_all and attrib, and semindex.evalagg and
semindex.evalgen. ana.py imports nothing outside the standard library (csv, json, math, os, re,
statistics, sys, collections.Counter) and reads perrun.csv, the frozen predict.txt and the two smoke
runs' meta.json.

perrun.py stops before writing in three cases, each of which would otherwise leave a cell's counts wrong
with nothing else saying so: a run whose discovery rows the evalagg output has not seen yet (the output is
older than the store), a DONE run that folds a number of polls.csv rows other than 8, which is the one row
per directed neighbour pair of the line h0 .. h4, and a reschedule row whose `trigger` is neither
`answered` nor `timed_out`. All 200 runs folded 8 rows each, 800 per cell. The fix for the first two is to
rerun the evalagg call and then perrun.py.

What each of them says, and what a zero there means. The first ten are evidence/09's record-set
counters, incremented in evidence/05/attrib.py at the lines named.

  dirs=200 done=200       200 seed directories exist under the stage and all 200 carry a DONE marker. A
                          smaller `done` would mean the analysis read a stage that is still being swept.
  exact_n=191300.0        the (record, node) pairs whose delay both this analysis and evalagg's
                          discovery.csv hold a time for (attrib.py:441).
  exact_within1=191300.0  of those, how many agree to within 1 ms. Equal to exact_n, so every pair agrees
                          (attrib.py:442).
  exact_maxerr=0.0        the largest difference between the two times. A zero means the delay of pass
                          line 5 is counted on exactly the arrivals evalagg counted (attrib.py:443).
  exact_censor_disagree=0 pairs this analysis calls censored while discovery.csv does not, or the reverse.
                          A zero means both sides leave the same records out of the delay
                          (attrib.py:434).
  exact_missing_in_discovery=0
                          in-window records with no discovery.csv row at all. A zero means no record was
                          timed against a row that is not there (attrib.py:430).
  runs_without_discovery_rows=0
                          runs with no discovery rows in the aggregation. A zero means every run's delay
                          rests on its own rows (attrib.py:420).
  stored_without_learn=0  records a node stored although no moment at which it learned of them is visible
                          in its log. A zero means the wait-and-fetch split is complete for every stored
                          record (attrib.py:376).
  hop_no_gap_before=0     record arrivals with no decision row before them on that (node, neighbour)
                          pair. A zero means every arrival has a decision to attribute it to
                          (attrib.py:387).
  reply_before_any_poll=0 state replies that arrived before that pair's first poll. A zero means no reply
                          was folded into a poll that had not been sent (attrib.py:272).
  neg_fetch=0             records whose fetch time came out negative, that is, stored before learned. A
                          zero means no leg of the chain runs backwards (attrib.py:382).
  sched_regen_diff 0      how many of a run's two record origins hold instants the committed generator
                          does not draw again for that (host, seed, k, workload). A zero over all runs
                          means the instants the testbed ran are the instants the prediction scored
                          (evidence/20/perrun.py's docstring, the `sched_regen_diff` entry).
  head_missing_disc 0     headline records with no discovery row, and
  all_missing_disc 0      the same over every scheduled record. A zero means no record the schedule names
                          vanished from the aggregation, which would deflate a run's counts in silence.
  node_logs 1000          200 runs times the 5 hosts of the line. A run with fewer logged its decisions
                          somewhere this analysis does not read, and its decision counts would be short.
  bad_action_prob 0       reschedule rows whose `action_prob` is other than 1/3, and
  bad_interval 0          reschedule rows whose `interval_s` is none of 3.695, 6.0, 10.043. Zeroes mean
                          the share per arm of pass line 4 is counted on the uniform draw this step ran.
  bad_draw_rows 0         the same two faults counted once per row, so a row wrong in both ways stays one
                          row.
  arm_other 0             reschedule rows that fell in neither of the three arm columns. The same
                          property as bad_interval, counted on the column side.

hop_gap_outside_window = 1600.0
-------------------------------
What it counts: while the per-hop breakdown is built, the decision row immediately before a record's
arrival at a node is read, and if that row's timestamp lies outside the measurement window the record is
skipped for the breakdown (evidence/05/attrib.py:390-392, the `continue` after the increment). It is
carried into the CSV as a column by evidence/09/perrun.py:27. It enters neither the 4-hop delay nor the
poll count, which is what evidence/16/README.md:93, evidence/17/README.md:111 and
evidence/19/README.md:142 record about it as well. This step reads no per-hop breakdown, so nothing here
is counted on the skipped records.

Whether 8 per run is the expected value: no file states an expected value for this counter, so the
question cannot be settled from the repository.
  - evidence/20 recorded no value for it at all. It appears in that directory only as a column name in
    perrun.csv; neither its README.md nor its RUN.txt names the counter. Summing that column for this file
    gives 2272 over its 200 runs, made up of 0 for `s10b3p695`, 76 for `s10b6p0`, 244 for `s10b10p043`,
    1412 for `s10t37r` and 540 for `s10f`.
  - The earlier steps that did record it report a stage total and no expectation:
    evidence/19/README.md:142 reports 380 over its 13 stages, evidence/17/README.md:111 reports
    684 / 648 / 88 / 44 / 0 over its five stages, evidence/16/README.md:93 reports 640 and 652 for its two
    rule stages.
  - 1600 over 200 runs is 8 per run as a mean and not a per-run figure. Summed per cell the column holds
    920 at p 0.2 and 680 at p 0.4, and per run it takes the values 0 (62 runs), 4 (29), 8 (39), 12 (32),
    16 (15), 20 (9), 24 (9), 28 (3), 32 (1) and 36 (1). Those two lines were computed for this file from
    perrun.csv's own column.
So what is recorded here is the count, its spread and what the counter counts. Nothing in the repository
says what it should have been.

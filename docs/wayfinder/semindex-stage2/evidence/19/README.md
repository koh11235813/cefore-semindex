# evidence/19: 入ったり止まったりする負荷を、実機で測った（2026-11-20〜21）

これまでの実測は全部、レコードが一定の調子で作られ続ける負荷（W0）だった。入ったり止まったりする負荷の上の数は、なぞり直し（evidence/14、15）にしか無かった。この段は、負荷を選ぶつまみ（`--workload`）を足して、2 つの負荷を実機で回した。合否の線となぞり直しの予測は、run の前に `spec.md` と `predict.txt` に置いた。チケットは `tickets/06-onoff-workload.md`。

| 負荷 | 形 |
|---|---|
| `wo` | 作る時間 20 秒と止まる時間 20 秒が交互 |
| `wv` | 作る時間と止まる時間の長さがばらつく（指数分布、平均 20 秒、4〜60 秒に切る） |

## 先に結論

- **なぞり直しは、入ったり止まったりする負荷でも実機を言い当てた。** 10 個の段の遅れと状態確認の数、合わせて 20 個が、全部 ±6 % の帯に入った（いちばん外れたのは +3.3 %）。読みは「predicted」。evidence/14 と 15 の、この負荷の上の数に、初めて実測の裏付けが付いた。
- **戻さない決まり（T37）は、どちらの負荷でも固定の間隔に負けた。** 固定の間隔の線に対する得は `wo` で -18.8 %（区間 -25.8〜-11.6）、`wv` で -15.1 %（-24.1〜-6.7）。読みは 2 つとも「reversed」で、予測どおり。今の負荷（W0）では -6.4 % で 0 と見分けられなかったものが、この負荷でははっきり負になった。
- **戻す決まり（T37r）は、どちらの負荷でも固定の間隔と見分けられなかった。** `wo` で +0.4 %（-10.8〜+10.3）、`wv` で +2.9 %（-8.9〜+13.7）。読みは 2 つとも「not seen」で、予測どおり。これは「上積みが無い」ことの証明になっていない。区間が効き目より広くて、どちら向きとも言えない。
- **2 つの決まりをそのまま比べると、差は今の負荷より大きい。** T37r は T37 より状態確認が `wo` で 32 %、`wv` で 29 % 多く、遅れが 30 %、29 % 短い（今の負荷では +27 % と -23 %）。どの区間も 0 をまたがない。
- 203 本は全部有効で、印は 0。門（今の負荷のまま新しいコードで回した 3 本）も通った。

## 2 つの採点

`spec.md` が先に決めたもの。見出しの採点は、作られる予定の時刻が t0+72 秒までのレコードだけを数える。入ったり止まったりする負荷では、遅い時刻に作られたレコードが測る窓の終わりまでに届かずに打ち切られる割合が大きいので、それを避けるために置いた。全レコードの採点は、これまでの段と同じ数え方。言葉は見出しの採点で読み、全レコードの値は横に置く。状態確認の数は、どちらの採点でも窓の全体で数える。

## 読み

- 空の答えで間隔を延ばして、時間切れでは戻さない決まり（T37）は、入ったり止まったりする負荷では固定の間隔より悪い。向きも大きさも、なぞり直しの予測どおり。理由として考えられるのは、止まっている時間に間隔が上限まで延びて、次に作り始めたときに気付くのが遅れること。ただし、これはわたしの推しで、この段は判断の列を追っていないので確かめていない。
- 時間切れで戻すこと（T37r）は、その悪さを消す。ただ、固定の間隔を超える上積みは、今の負荷でも、この 2 つの負荷でも、見分けられなかった。3 つの負荷を通して、T37r は「状態確認を 3 割ほど増やして遅れを 2〜3 割縮める」という、固定の間隔の線にほぼ沿った動きをしている。
- なぞり直しは、3 つの負荷、固定の腕、時間切れに反応する決まりの全部で、実機の遅れを 6 % の中で言い当てた（この段では 3.3 % の中）。式の決まりを比べる道具として、p 0.4 のこの切断の形の上では、実機の代わりに使える裏付けが増えた。

## 読むときの注意

- **合否の線 5 のうち、固定の腕の「状態確認の数」6 個は、当たって当然の数。** なぞり直しは、同じ seed の切断の時刻表の上で状態確認を並べ直す。固定の間隔で送る回数は負荷で変わらないので、ここは予測というより写しに近い。当たったと言えるのは、遅れの 10 個と、決まりの段の状態確認の数 4 個。その 14 個のずれは -1.0〜+3.3 %。
- **遅れのずれは、10 個のうち 8 個が正。** 実機のほうが、なぞり直しより 0.1〜3.3 % 遅い。帯の中だが、片側に寄っている。理由は調べていない。
- **`wv` の T37 は、全レコードの採点では「reversed」の端にいる。** 区間は -14.91〜-0.37 で、上の端は 0 まで 0.37 ポイント。遅れの出し方は、レコードを全部合わせた平均（`spec.md` と `predict.py` の決まり）。run ごとの平均をさらに平均する出し方だと、この 1 行は 0 をまたぐ（-14.60〜+0.53。確かめ役が手元で出した値で、この段の csv と md には入っていない）。見出しの採点では、どちらの出し方でもはっきり負。
- **区間の幅は、`spec.md` の見込みより狭かった。** `spec.md` は「実機の区間は、なぞり直しの 1.4 倍くらい広く出て、半幅は 11〜14 ポイントになる」と書いていた。実測の半幅は 7.1、10.6、8.7、11.3 ポイントで、なぞり直しの 0.9〜1.2 倍。今の負荷で 1.4 倍に広がった理由も、今回広がらなかった理由も、分かっていない。
- **合否の線 5 は、作る時刻が負荷の決めた形になっていることを示していない。** 予測は、実機と同じ生成の関数から時刻を読んでいる。形が決めたとおりであることは、`tests/test_evalgen.py` が見ている。
- 全レコードの採点では、打ち切りの割合が大きい（固定 10.043 秒の腕で 24〜27 %）。遅れは届いたレコードだけで平均するので、打ち切りの多い段ほど短めに出る。見出しの採点を言葉に使うのは、このため。
- `spec.md` に選びの余地があった所は 9 つ。`results.md` の最後の節に並べてある。どれも、今回の数では読みを変えない。
- 1 つのマス（p 0.4）、1 つの切断の形だけ。ほかの p には何も言えない。
- 集計の点検の数 `hop_gap_outside_window`（`perrun.csv` の同じ名前の列を段ごとに足した値。`results.md` には出ない）は、`s9wv_t37` 108、`s9wv_t37r` 104、`s9wo_t37` 60、`s9wo_t37r` 60、`s9w0_t37r` 28、`s9wv_b10p043` 12、`s9wo_b10p043` 8、残りの 6 段は 0、合わせて 380。ホップごとの内訳を作るときに窓の外の判断に当たった回数で、4 ホップ先までの遅れと状態確認の数には入らない。

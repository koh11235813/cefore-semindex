# 答えが返ったのに新しいものが無かった状態確認を数えた（`s5*`・`s6*`）

利用者からの問い「状態確認のうち、答えは返ったが新しいレコードを一つも運んでこなかったものはどれくらいあるか」に答えるための数え直し。間隔を決めるだけの方針に対して、状態確認そのものを送るかどうかも決める学習された方針なら、式で決まる方針に勝てる余地がある。その余地の大きさと、余地がどこから来ているかを測った。

run は新しく回していない。`evidence/09/`（5 秒の枠）と `evidence/10/`（8〜12 秒の切断）の `s5*`・`s6*` の 840 本を、別の数え方で読み直しただけ。

## 数えたもの

単位は run ごとの向きつきの組（ノード、隣）で、窓は `polls.csv` と同じ `[t0+10 秒, t0+130 秒]`。定義は `emptypoll.py` の docstring と `tables.md` の Legend にそのまま置いた。主なものは次の 4 つ。

| 数 | 中身 |
|---|---|
| `state_rx` | 窓の中で隣から返ってきた状態確認の答え（遅れて届いた答えも含む） |
| `rx_no_new` | その答えの `hi` に載っている origin のすべてで、seq 1..hi をノードがすでに持っていた答え。空の `hi` も含む。答えが届いた時点での真の値 |
| `rx_hi_unchanged` | 同じ隣からの前の答えと `hi` が origin ごとに同じだった答え。隣の通知だけを見た、狭い信号 |
| `rx_no_fetch` | 答えの次の行が、同じ隣・同じ ts_ms の `fetch_plan` ではなかった答え。実際に engine が取得を計画しなかったもの |

`rx_no_new` を、なぜ新しいものが無かったかで 4 つに分けた（先に当たったものを採る。4 つの和は `rx_no_new` に一致する）。トポロジーは h0-h1-h2-h3-h4 の直線で origin は h0 と h4 の両端なので、ある隣から新しく来うるのは、その隣の側の origin だけ。ノード hn が hm からの答えを受けるとき、側の origin は m < n なら h0、そうでなければ h4。

1. `all_complete`: 両方の origin のレコードをノードが全部持っている（`rx_after_complete` と同じ。行ごとに一致を確かめた）。
2. `side_complete`: 側の origin のレコードはノードが全部持っているが、両方の origin の全部ではない。
3. `side_none`: 答えの側の origin の `hi` が 0 か、そもそも載っていない。その origin のレコードがまだ隣に届いていない。
4. `during`: 残り。隣は側の origin のレコードをいくつか持っていて、ノードは 1..hi を全部持っていて、続きはまだ来る。レコードが伝わっている途中の空で、生成が終わった後の、まだ届ききっていない時間のものも入る。

バイトは `evidence/09/ana.py` の定数バイトのモデル（`B_const`）をそのまま使い、空の答えの値段を `INT_B + REP_B[p]` として `empty_B` を出した。`REP_B` は p 0・0.2・0.4 にしか値が無いので、p 0.5・0.6 のマスは数と割合だけ。

### 3. 先を全部知っていたときの上限と、前もって決めた比

- 空の答えだけをちょうど避けられたとすると（`empty_B`）、状態確認のバイトは短縮で 47 %（p 0.2）と 43 %（p 0.4）、5 秒待ちで 49 % と 44 %、固定 10.043 秒の腕で 52 % と 47 % 減る。二つの方針と固定 10.043 秒の腕では 43〜52 % で、この大きさは方針に特有のものではない（`s5` の同じ三つの p 0.2・0.4 では 42〜52 %）。間隔の短い腕では空の割合が高いぶん大きく、`s6` の 0.5 秒の腕で 82 % と 75 %。
- `empty_B` は、先を全部知っている参照の値で、実際の決まりが届く値ではない。「遅れを変えずに省ける額」そのものでもない。`rx_no_new` は `hi` までしか見ていないので、空とした答えのうち全マスの合計で 9 件は、隣の飛び飛びの持ちぶん（`extra`）から取得を起こしていた（5. の食い違い）。その答えまで省くと、その取得の時刻が動く。
- 前もって決めた比 `empty_B / excess_B`（`excess_B` は方針のバイトから同じ p・同じ seed の 10.043 秒の腕のバイトを引いたもの）は、短縮が 3.69（p 0.2）と 1.76（p 0.4）、5 秒待ちが 5.30 と 2.26。1.8〜5.3 で、どれも 1 を超える。
- ただし、この比が 1 を超える理由は、腕そのものが空の答えをたくさん受けているからで、方針の余分な状態確認が無駄だからという読みは当たらない。腕の `empty_B` は 8.02 B（p 0.2）と 5.89 B（p 0.4）あり、方針の `excess_B`（1.58〜4.08 B）より大きい。
- p 0 では切断が無く、方針は腕と同じ状態確認を送るので `excess_B` はほぼ 0（−0.01 B と +0.03 B）。p 0 の比（−1637 と +328）に意味は無い。

### 4. 方針から見えるもの

四つを分けて読む。

- 答えが届いた時点では、それが空だったかどうかをノードは計算できる。engine はこの比べから取得を計画している（5. のとおり `rx_no_fetch` と `rx_no_new` は 83 件しか食い違わない）。
- 一つの `state_poll` の判断の状態には、その結果は残らない。空だったかどうかに関わる中身として載っているのは、判断の時点の自分の origin ごとの `hi` と `missing`、隣ごとの通知の `hi` と `notified_max`（`tracker.decision_state`。ほかに、その隣への取得中の数、直前の状態確認に返事が来たか、返事の来なかった連続の数なども載るが、答えが空だったかどうかをそのまま示すものは無い）。届いた答えが運んできたものを次の判断までに取り終えると、空だった答えの後と同じ形になる。実物では、`s6short` の p 0.2・seed 1 の h1 で、h0 からの答えが届いた時に 36 件足りず、次の `state_poll` の判断では `hi` 36・`missing` 0 になっていた。
- 同じ隣についての続く二つの判断の状態を比べると、あいだに届いた答えが空だったかどうかが、ほぼ分かる。見るのは、自分の側の origin の `hi` が進んだかどうか。あいだに届いた答えが 1 つだった場合を 42 マスで合わせると、空だった答え 216489 件では一度も進まず、新しいものを運んだ答え 59109 件のうち 59032 件で進んだ（`recheck.txt` の `seq_*`）。進まなかった 77 件は、0.5 秒の腕で 35 件、1.359 秒の腕で 27 件、3.695 秒の腕で 11 件、方針で 4 件。`s6` の方針と 10.043 秒の腕の p 0.2・0.4 の 6 マスでは外れが無い（空 4061 件、新しいもの 3924 件）。この見分け方は、前の状態を覚えておくこと、側の origin の決め方（直線のトポロジー）、答えが運んできた seq の取得が次の判断までに着くことに頼っている。
- これから送る状態確認の答えが空になるかどうかは、どの方針からも見えない。

数える前に「方針が見られる信号」と呼んでいた `rx_hi_unchanged`（隣の `hi` が前の答えと同じ）の数は、次のとおり。

- `s6` の方針で 0.37〜0.39 で、真に空だった 0.53〜0.55 より低い（`s5` の方針の p 0.2・0.4 では 0.32〜0.36 と 0.51〜0.53）。
- 差の 0.15〜0.17 は、隣の `hi` は進んだのに、その seq をノードがもう持っていた答え（`s6` の方針の 4 マスで 1 マス 232〜256 件。`s5` の方針の p 0.2・0.4 では 0.15〜0.19、257〜279 件）。逆向きの食い違い（`hi` は同じなのにノードの足りないものが残っていた答え、`hi_unch_but_new`）は、840 本の全マスで 57 件しかない。
- 隣の通知の `hi` が変わったかどうかも、続く二つの判断の状態から見える。ただし判断の状態が持つのは最新の通知だけなので、答えごとの `rx_hi_unchanged` とは同じ数にならないことがある（あいだに答えが 2 つ以上届いた答えは、全マスの合計で 8 件）。
- 状態確認を省く決まりを作るなら、直前までの答えが空だったことから、次の答えが空かどうかを当てる形になる。その当たり具合はここでは測っていない（「推したもの」に回した）。

2026-11-12 の訂正: 数える前は `rx_no_new` を「方針には見えない真の値」、`rx_hi_unchanged` を「方針が見られる信号」と呼んでいた。上のとおり、空だったかどうかは届いた時点でノードが計算でき、続く二つの判断の状態からもほぼ分かるので、この呼び方は外れていた。

### 5. `rx_no_fetch` と `rx_no_new` の食い違い

- 840 本・6720 組で 83 件だけ食い違った。取得を計画しなかったのに新しいものがあった 74 件（内訳は `backoff` 58、隣ごとの同時取得の上限（`cap`）9、すでに取得中（`in_flight`）7、ほかの理由（`other`）0）と、空なのに取得を計画した 9 件（すべて `extra`、つまり `hi` より上の seq を取りに行ったもの）。
- つまり「engine が取得を計画しなかった答え」と「真に新しいものが無かった答え」は、ほとんど同じものを指している。食い違った答えの実物は `mismatch_examples.txt` に理由ごとに 1 件ずつ置いた。

## 測ったもの、推したもの

- 測った: 状態確認の数と答えの数、空の割合（真の値）、`hi` が変わらない割合、engine が取得を計画しなかった割合、空の 4 分け、向きごとの 4 分け、`empty_B` と `B_const` と `excess_B`、`rx_no_fetch` との食い違いの数と理由。
- 推した（測っていない）:
  - 全部そろった後の部分（`all_complete`）は、空の答えが続くあいだ間隔を延ばし、新しいものが来たら戻す形の決まりで取れると見ている（Trickle、RFC 6206 の形）。届き始める前の部分（`side_none`）も同じ形で取れるはずだが、間隔を延ばしたぶん、最初のレコードを見つけるのが遅くなる。遅れがどれだけ増えるかは測っていない。
  - 戻す合図を「隣の `hi` が変わった」にすると、4. のとおり答えの 0.15〜0.17 で空振りする（`hi` は進んだが新しいものは無い）。「新しいものがあった」を合図にすれば、この空振りは起きない。この合図は一つの判断の状態には残らないが、4. のとおり、前の状態を覚えておけば、自分の側の origin の `hi` が進んだかどうかから、いまの判断の状態のままで作れると見ている。いまの方針の表は、返事の来なかった連続の数だけを読む。一つの状態だけを読む形のままにするなら、届いた時の比べの結果か、空が続いた回数を、判断の状態に足すことになる。
  - 4. の差（`hi` は進んだのに空）は、ノードが反対側の隣から先に取ってきたレコードを、隣が後からそのノードから取って通知したものだと見ている。数では確かめていない。
  - origin の隣で `during` が 0 になるのは、状態確認の間隔が生成の間隔（2 秒）より長く、生成が続くあいだは origin の `hi` が答えのたびに進んでいるからだと見ている。間隔が 2 秒より短い腕でだけ 0 にならないことは、この見方と合う。
  - `during` は、生成の山の形を知っているだけでは避けられない部分で、`s6` の p 0.2・0.4 の方針と 10.043 秒の腕の間隔では、状態確認のバイトの 6.7〜10.9 % に留まる（`s5` の同じ三つと p 0 を入れると 4.8〜11.2 %）。だから、この負荷とこの間隔の範囲では、学習された方針が式で決まる方針に勝てる余地は小さく、差を見るには、生成が不規則だったり長く続いたりする負荷が要ると見ている。いまの負荷は、1 分ほどの生成の山が 1 つあるだけ。
  - 直前までの答えが空だったことから次の答えが空かどうかを当てられるか（4. の当たり具合）は測っていない。当たるかどうかで、省く決まりが作れるかが決まる。

## 確かめたこと

- `polls_sent`・`state_rx`・遅れて届いた答えの数は、`s6` では evalagg の `polls.csv` の 3840 組すべてと一致し、`s5` では `evidence/09/perrun.csv` の 360 本すべてと一致した（`tables.md` の先頭の行）。
- 4 分けの和は `rx_no_new` に一致し、`all_complete` は `rx_after_complete` に一致した。`perpair.csv` の 6720 行すべてと、42 マスすべてで確かめた（`RUN.txt` と `tables.md`）。
- `B_const` は `evidence/09/` と `evidence/10/` の `live_main.csv` の値と、バイトのある 30 マスすべてで一致した（差の絶対値の最大は 5.68e-14。`tables.md` のバイトの表の下の行）。`perrun.csv` の `ngap` の和と `polls.csv` の `polls_sent` は、バイトのある 30 マスすべてで完全に一致した（p 0.5・0.6 の 12 マスは、この台本では比べていない）。
- 台本は 2 回回して、`perpair.csv`・`cells.csv`・`tables.md`・`mismatch_examples.txt` と標準出力がバイト単位で同じ。
- 4 分けを足す前の下書きと比べて、もとからあった列は値がすべて同じ（`perpair.csv` 6720 行 × 21 列、`cells.csv` 42 行 × 50 列、差 0 件）。4 分けの割合の bootstrap は別の乱数の流れから引いていて、ほかの列の CI を動かさない。
- `recheck.py`（`emptypoll.py` とも semindex のパッケージとも台本を共有しない、別に書いた数え直し）: 各ノードの `events.jsonl` を json だけで読み、42 マス・6720 組のすべてで `polls_sent`・`state_rx`・`rx_no_fetch`・`rx_no_new`・`rx_hi_unchanged`・`rx_after_complete` と 4 分けの 4 列を数え直して、`perpair.csv` と比べた。差は 0 件（`recheck.txt`）。`mm_*` の列（食い違いの理由）、`late_replies`、`hi_unch_but_new`、`cells.csv` の割合・CI・バイトは、この台本では数え直していない。`recheck.txt` には、`perpair.csv` に列の無い数も二つ載せた（比べる相手は無い）: `during_after_gen`（結果の 2.）と `seq_*`（結果の 4.）。4 分けは、`emptypoll.py` を書いた側には定義の文だけを渡し、`recheck.py` の側の台本を見せずに書かせたもの。

## 読むときの注意

- `B_const` の「答えが返った状態確認」（`ngap − nnorep`、4 ホップの discovery の行から数えたもの）と `state_rx`（`polls.csv` の答えの行）は、バイトのある 30 マスのうち 25 マスで完全に一致し、残る 5 マスで 1〜2 件ずれる（最大は s6b0p5 p 0.2 の 2 件）。空の答えを `REP_B` で値づけする誤差はこの範囲。
- 一つの `state_poll` の判断の状態には、直前の答えが空だったかどうかは載っていない（結果の 4.）。この数え直しの `rx_no_new` は、ログから後で組み立てた値。
- `hi: {}` は、本当に空の答えのときにも、答えの読み取りに失敗したときにも書かれるので、ログからは区別できない。どちらも `rx_no_new` に入る。
- `state_rx` には隣の `hi` しか載らないので、隣が飛び飛びに持っている `extra` は見えない。`rx_no_new` は `hi` までの範囲での真の値。
- p 0.5・0.6 には `REP_B` の値が無いので、そのマスは数と割合だけ。バイトの話は p 0・0.2・0.4 のマスに限る。
- 側の origin の決め方は h0-h1-h2-h3-h4 の直線のトポロジーに頼っている。結果の 4. の、続く二つの判断の状態からの見分け方も同じ。枝のあるトポロジーでは、側の origin の決め方から作り直しが要る。

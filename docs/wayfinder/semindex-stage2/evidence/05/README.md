## 判断ごとの割り当ての決まり

ノード n と、origin o のレコードの上流の隣 m（直線で o に 1 歩近い隣）について:

- 判断 i は、n が m に出した状態確認 1 回（時刻 t_i）。受け持ちは、次の m への状態確認までのあいだ（t_i, t_{i+1}]。終わりは適用した間隔から計算せず、次の状態確認の実際の時刻を使う。
- レコードが m に届いた時刻は、m の `record_stored`（m が origin なら `record_created`）。受け持ちのあいだにこの時刻があるレコードを、判断 i に割り当てる。
- n がそのレコードを知った時刻は、届いた時刻より後で、そのレコードを含む m からの最初の返事（`state_rx`）。返事の記録には `hi` しか無いので、`hi` より先の飛び飛びの番号（`extra`）は、m の保存の記録から返事の時点の中身を組み立て直して判定した（使ったのは 0〜4.4%）。知った時刻より前に、n が m への取得の計画でそのレコードを挙げていたときは、計画の時刻を知った時刻にした（0〜0.48%）。返事から決まらず計画の時刻だけで決めたものは 0.005% 以下。
- 待ちは、届いてから知るまで。続く状態確認がタイムアウトして延びたぶん（延び）も、判断 i に割り当てたまま。取得は、知ってから n に保存されるまで。ホップ数 h は n と o の位置の差（1〜4）で、重みは掛けていない。
- 窓は evalagg と同じ（t0 + 10 秒〜t0 + 130 秒）。窓の終わりまでに保存されなかった組は打ち切りとして別に数え、受け持ちが窓より前に始まった判断（`s2b10p043` で 128、`s2a` で 3988 のレコード・ホップ）は腕ごとの値から外した。
- 腕ごとの値は、レコード 1 件・1 ホップあたりにそろえた（受け持つ時間が腕によって 20 倍違うので、判断 1 回あたりの平均は比べられない）。選ぶ確率がどれも 0.25 なので、重要度で重み付けした見積もりは、腕ごとの比と同じになる。

## わかったこと

### 1. 割り当ては矛盾なくできる（`checks.csv`）
- ホップごとの「待ち＋取得」を足すと、打ち切られていない 953,533 組のすべてで、evalagg の発見の遅れ（`discovery.csv`）と 0 ms の差で一致した。ホップごとの時刻の差を足しているので、この一致はほぼ自動的に成り立つ。

- 取得が 1 件だけ出ているときは 1〜2 ms で受け取る。リンク、cefnetd、上流のエージェントを合わせた往復はそのくらい速い。同じ隣に出ている取得が増えるほど受け取り待ちが延び、1 件増えるごとにおよそ 50 ms 延びる（2〜4 件で 90〜150 ms、5〜8 件で 230〜500 ms、上限 32 の 9 件以上で 905 ms）。
- コードで確かめたこと: 取りに行く側のエージェントは、受け取った Data を 1 回のループで 1 件ずつ処理する（`cefpyco_transport.py` の `poll`）。1 件の処理では、中身の検証とハッシュのあと、1 件ごとに SQLite のトランザクションを commit する（`store.py` の `append_received`。WAL で `synchronous` は既定の FULL なので、commit ごとに fsync が走る）。`record_stored` の時刻は、その処理の前に読んだ時刻で打たれる（`engine.py` の `on_record`）。そのため、k 件目の受け取り待ちには、前の k − 1 件の処理の時間が入る。
- 測ったこと: 同じループの中の `record_stored`（処理の前）と、すぐ後の `fetch_plan`（処理の後）の時刻の差は、受け取った 1 件を処理する区間の時間になる（`commit_time.py`）。この区間には、検証、ハッシュ、INSERT と進捗の更新、commit、進捗の読み出し、時間切れの確認が入る。中央値は 33〜74 ms で、k が大きいほど長い（試走の k = 1 で 33 ms、k = 8 で 74 ms、本番の B 0.5 秒で 66 ms）。処理が終わったとき、次の Data はもう届いている（待ちの中央値 0 ms）。
- 推定していること: この区間の大半は commit の fsync だと見ている。1 件ごとに fsync する設定であることと、この VM では 5 つのエージェントのデータベースが 1 本の仮想ディスクに載っていて、書き込み 1 回の平均が 19 ms あることが根拠。k が大きいほど延びるのも、ほかのノードの commit とディスクを取り合うためと見ている。区間の中の内訳は測っていない。
- 上限 8 の空き待ちは、短い固定の間隔（0.5 秒・1.359 秒）では 0、3.695 秒で取得の 9%、10.043 秒で 49%、A で 45%。上限は、返事で新しく知った件数が少なくても、前の返事の取得が残っていれば効く。上限を 32 にすると空き待ちは減るが（試走で 807 → 112 ms）、そのぶん受け取り待ちの列が長くなり、9 件以上では 905 ms になる。その先は Interest の寿命（2 秒）を超えて時間切れになる（`evidence/04/` の上限の表）。上限は、受け取りの遅さが生む待ち行列を、エージェントの中に置くか、ソケットの側に置くかを決めているだけ。試走の 2 行は 3 seed ずつで、p = 0.4 の切断も混ざる。上限 32 の試走は上限 8 の試走の 3 時間ほど後に回していて、その間に、受け取った 1 件を処理する区間の時間の中央値も短くなっていた（k = 4 で 49 → 33 ms）。上限 32 の数字には、回したときの条件の違いが入っているかもしれない（ディスクの状態がどれだけ効いたかは確かめていない）。
- まとめると、待ちを生んでいるのは受け取る側の 1 件ごとの処理だと測れた。その主な原因は、1 件ごとの fsync と、仮想ディスク 1 本を 5 ノードで分ける試験台だと推定している。取得が 1 件だけなら 1〜2 ms で返ることと、処理のあと次の Data がもう届いていることから、Cefore や回線の寄与は小さいと見ているが、複数の取得が出ているときの送る側の寄与は、この記録だけでは除けない。確かめの計測（`synchronous` を下げる、データベースを tmpfs に置く）は、まだしていない。
- 2026-10-29 訂正: 報告の途中で、A の取得が長い理由を「上限の 8 件を超えたぶんが待たされるから」と書き、次に「主な原因は上流の 1 件の時間で、上限は 17 件以上のまとまりのときだけ効く」と直した。どちらも誤りだった。上限は前の返事の取得が残っていれば小さなまとまりでも効き（レビューの指摘）、1 件の時間として見えていたのは、主に取りに行く側が受け取った 1 件を処理する時間だった。

## 外れた想定
1. `state_rx` の記録に `extra` があること。記録は `hi` だけだった（上の割り当ての決まりで組み立て直した。エージェントの `notified_max` と食い違うのは、`s2a` で 2.7%、B で 2.2〜11% の返事で、レコード・ホップの 0.5% 以下に当たる）。
2. 返事を受け取った時刻の holder の中身が、返事の中身と同じであること（`evidence/04/breakdown2.py` の決まり）。返事の 4.9〜11.4% で多めに数えていた。`state_rx` の時刻は n が処理した時刻のため。通信量の組み立て直しは breakdown2 の決まりのまま、中身の判定は状態確認を送った時点の下限を使った。
3. 受け持ちのあいだが、適用した間隔と同じ長さであること。実際は平均 52〜74 ms 長い（0.5 秒の腕では 12%）。
4. 知った時刻が、最初の取得の計画の時刻と同じであること。同じ ms なのは 31.5〜81% だけで、残りは同時取得の空きを待っていた。
5. ホップの結果が n の腕だけで決まること（上の 2.）。
6. p = 0 の「待ち ÷ 選んだ間隔」がどこでも 0.45〜0.6 に入ること。20 のうち 2 つが外れた。0.5 秒のホップ 1 の 0.68 は、返事のあとの 88 ms と受け持ちの超過で説明がつく（受け持ちの中の待ちだけなら 0.50）。10.043 秒のホップ 2 の 0.61 は説明がついていない。全ノードが 10 秒ごとに同じ時刻から状態確認する段なので、隣どうしの位相がそろっているのかもしれないが、確かめていない。

## 確かめていないこと
- `state_rx` には状態確認の epoch が無いので、返事は「それより前の最後の状態確認」に結びつけた。リンクが揺れているときは、遅れて来た返事を 1 つ後の状態確認に結びつけることがある。これはバイト数の判断ごとの値と延びの分け方に効き、ホップごとの待ちと取得の合計には効かない。
- バイト数の組み立て直しは、`counters` と突き合わせ直していない（breakdown2 の式をそのまま使った。breakdown2 は `evidence/04/` で突き合わせ済み）。
- まとまりと位相のそろいという 2 つの因果の読みは、まとまりの大きさと内訳だけに基づく。切り分ける実験はしていない。

## ファイル
- `main2.sh`: 本番の台本（root で `sudo bash main2.sh`）。
- `attrib.py`: 1 回の run の割り当て（上の決まり）。`run_all.py`: 全 run を 6 プロセスで回し、層ごとの和をまとめて CSV を書く。`make_tables.py`: CSV から `tables.md` を書く。
- `per_hop_B.csv`: 段 × 腕 × p × ホップごとの待ち・受け持ちの中の待ち・返事のあと・取得・延びの割合・バイト数・まとまりの大きさ・待ち ÷ 選んだ間隔。
- `predicted_vs_B.csv`: A からの見積もりと B の実測を、腕 × p × ホップと 4 ホップ先の端から端まで並べたもの（誤差、打ち切り、印つき）。
- `state_buckets.csv`: A の判断を `last_poll_status` × 連続タイムアウト（0・1・2・3 以上）× p で分け、区分と腕ごとの受け持ちの数・レコード・ホップの数・待ち・バイト数・たまる速さ・順位（待ちだけ、待ち + λ・バイト、λ = 1・10 ms/B）。
- `checks.csv`: 一致の確かめ、知った時刻の決め方の内訳、上流以外の例外、延びの割合、打ち切り。
- `fetch_by_inflight.csv`: 判断の時点で取得が 0 件だったかどうかで分けた取得時間（待ち行列の混ざりの確かめ）。
- `raw_sums.json.gz`: 層ごとの和（ストアを読み直さずに別の切り方をやり直すため）。
- `tables.md`: `make_tables.py` が書いた表の全体（英語）。
- `capbind.py`・`capbind.txt`: 上の 4. の 1 つ目の表の数え方と出力。
- `fetchsplit.py`・`fetchsplit.txt`: 上の 4. の 2 つ目の表（取得の時間を空き待ちと受け取り待ちに分けたもの）の数え方と出力。
- `commit_time.py`・`commit_time.txt`: 上の 4. の、受け取った 1 件を処理する区間の時間（段ごとの分布と、そのあと次の Data を待った時間）。
- `indep_check.py`・`indep_check.txt`: `attrib.py` とは別に書いた抜き取りの確かめ（B の 4 ホップ先の平均、ホップ 1 の待ち ÷ 間隔、取得の計画の大きさ）と出力。結果は B の 4 ホップ先が 1489・3269・8591・25258 ms（`predicted_vs_B.csv` と同じ）、ホップ 1 の待ち ÷ 間隔が 1.359 秒で 0.562（同じ）、0.5 秒で 0.676（`per_hop_B.csv` は 0.680、窓の切り方の違い）。
- `main_summary.csv`: 上の「回した段」を参照。

## 作り直し方
evalagg の出力が要る（`discovery.csv` が段ごとに 15 MB ほどあるので、ここには置いていない）。

```bash
AGG=<出力先>; ST=/home/lab_shared/semindex-eval
for s in s2c s2b0p5 s2b1p359 s2b3p695 s2b10p043 s2a; do
  MPLCONFIGDIR=$(mktemp -d) PYTHONPATH=src .venv/bin/python3 -m semindex.evalagg --store $ST --stage $s --out $AGG/$s
done
D=docs/wayfinder/semindex-stage2/evidence/05; OUT=<出力先>
PYTHONPATH=src:$D .venv/bin/python3 $D/run_all.py --agg $AGG --store $ST --out $OUT
.venv/bin/python3 $D/make_tables.py --dir $OUT > $OUT/tables.md
.venv/bin/python3 $D/capbind.py --store $ST
.venv/bin/python3 $D/fetchsplit.py --store $ST
.venv/bin/python3 $D/commit_time.py $ST t2k1 t2k2 t2k4 t2k8 t2c32k4 t2c32k8 s2b0p5 s2b10p043 s2a
.venv/bin/python3 $D/indep_check.py --agg $AGG --store $ST
```

`run_all.py` は 1000 回を 6 プロセスで 14 秒ほどで読む。`--agg` と `--store` の既定値は、ここの CSV を作ったときの場所（`--agg` はそのときの作業用のディレクトリで、いまは残っていないことがある）。行の順番はプロセスの終わる順で変わることがあるので、比べるときは行を並べ替えてから比べる。

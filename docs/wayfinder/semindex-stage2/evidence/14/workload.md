Each workload is a function of (p, seed, origin) through `random.Random(f"ev14:{name}:{p}:{seed}:{origin}")`, so every rule sees the same creation times on one (p, seed) and the two origins are independent. All times lie in [t0+13 s, t0+110 s], so every record has at least 20 s before the window ends at t0+130 s. The outages, agent_start, t0 and the topology are the donor run's own and are not replaced.

## Gain per workload, cell and rule

`gain = 1 - delay(rule) / delay_frontier(polls_sent(rule))`, the frontier being piecewise-linear log(delay) over log(polls_sent) through the seven simulated fixed arms of the same cell and workload. Positive = faster than a fixed interval costing the same number of polls. `save` is the same statement read as polls saved at equal delay. 95 % intervals: 2000-resample bootstrap over the 20 seeds, `default_rng(20261117)`, frontier and rule recomputed from the same resampled seeds. A resample that puts the rule outside the arms' range yields no value, so an interval resting on fewer than 2000 resamples says so.

## Assumptions and deviations from spec.md

1. **A cell with no gain can only produce "mixed".** spec.md's reading rule says what a gain above zero and a gain at or below zero mean, but not what a cell without a gain does. Such a cell satisfies neither side here, so it cannot contribute to "does not help" (which needs all 3 cells) and counts towards "mixed".
2. **The non-monotone rule is applied to WR only**, as spec.md words it. If the WP or WB frontier comes out non-monotone the gain is still printed, with the flag beside it, which is how evidence/13 reported the one non-monotone cell it had. The `frontier_monotone` and `gain_suppressed` columns of `workload_gain.csv` separate the two.
3. **The gap columns are ../13/after.py's measurement with the record count parameterised.** after.py tests `len(held) >= 240`; WR creates 24 records per run, so the imported version would report zero polls after completion everywhere. The reply-side gap columns of after.py (gap before an EMPTY reply against gap before a non-empty one) are not recomputed here, because this step does not ask for them. after.py pooled replicate 0 only; these columns pool all 5 replicates. "polls after complete" counts the in-window state polls of all 5 nodes of a run that were sent once that node already held every record of the run, divided by the 100 (seed, replicate) runs, so it is a per-run count over the whole topology, not a per-node one.
4. **The three added fixed arms (0.8, 2.2, 6.0 s) are the spec2 rule with m = 1 and I_min = I_max**, which ../13/identity.py shows produces the same events as a fixed arm. With m = 1 the due instant never moves at a resolution, so the rule path consumes the tick-lag stream in exactly the order a fixed arm does (../13/trickle.md deviation 7c, measured by identity.py in Mode B as well as Mode A): the seven arms are one kind of arm, not two. The four testbed arms keep their stage settings and the fixed code path, which is what makes the W0 check exact for them.
5. **The tick-lag stream seed is `trickle:{donor}` for every workload**, the literal string of ../13/trickle.py. W0 only reproduces ev13 with that stream, and reusing it for the other three workloads pairs the lag stream across workloads too. Only the seed is shared between rules: they draw different numbers of lags per poll, so the values diverge from the first interval change on. The lag is at most 100 ms against intervals of 500 ms and more.
6. **The bootstrap's unit is the seed, each seed's value being the mean over its 5 replicates**, while the point estimates pool all 100 (seed, replicate) runs. This is ../13/trickle.py's deviation 2, inherited with its code: for sums the two orders agree exactly, for the ratios they differ in the last digits.
7. **Bytes use the same `REP_B[p]` for every rule**, as evidence/13 does: the mean reply size is taken not to depend on the rule, and on a replaced workload it is taken not to depend on the workload either, which is a second assumption nothing here checks. The headline is stated in polls_sent, not in bytes.
8. **Delay is the 4-hop uncensored mean**, so a rule that loses records to the window looks faster than it is. That is what the cens flag and the cens4 column are for.
9. **No tuning.** The workloads, arms and variants listed in spec.md are the only ones run, and every number is reported as it came out.
10. **What the replaced workload does not change**: the outage timeline, the record fetch machinery, the reply size model and the simulator itself. What it cannot carry over is validation: ../13/validate.md measured the replay against the logged workload, and a workload with a different shape may exercise the simulator where no measurement has ever checked it. The sub-2 s variants (T05, T136, T136s, T136c) additionally run source branches that no logged run reaches, as ../13/trickle.md deviation notes.

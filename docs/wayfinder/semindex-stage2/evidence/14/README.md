# evidence/14: 負荷を替えても、間隔を延ばす決まりは固定の間隔を越えない（2026-11-17）

evidence/13 は「空の答えが続くあいだ間隔を延ばす決まりは、今の負荷では固定の間隔に負ける」と出し、理由を「今の負荷は 2 秒おきに作り続けるので静かな時間が無いから」と推した。
ここでは、その推しを新しい run なしで確かめた。切断の時刻表は今の run のまま、レコードを作る時刻だけを替えて、同じなぞり直し（`../13/replay.py`、手を入れていない）で同じ決まりを比べた。

**ここの数字は全部なぞり直しの値で、しかも替えた負荷には照らす実測が無い。** なぞり直しを実測と照らしたのは今の負荷まで（evidence/13）。どの実機 run を回す価値があるかの見当として読む。

## 先に結論

- **推しは外れた。** レコードがまれに来る負荷でも、まとまって来る負荷でも、延ばす決まりは固定の間隔を越えなかった。先に書いた読み方（`spec.md`）で「効く」になった決まりは、どの負荷にも無い。
- 最短 3.695 秒のもの（T37）が速いのは、切断が無く、生成が続いているマスだけ（今の負荷で +18 %、始まりと周期を run ごとに替えても +17.5 %）。まとまりやまれな負荷では、そのマスでも得が消える。
- 打ち切りの偏り（下の「足した測り」）を除いても、読みは変わらなかった。

## 測ったもの、推したもの

測った（なぞり直しの上で）: 上の表。

推した（測っていない）:

- evidence/13 の推し「静かな時間があれば延ばす決まりが勝つ」は外れた。外れた理由を、今はこう見ている。このプロトコルは聞きに行くだけで、隣から知らせは来ない。間隔を延ばしているあいだに隣へ届いたレコードは、次に聞くまで見えないので、延ばしたぶんがそのまま遅れになる（4 ホップぶん重なる）。新しいものが来て最短に戻しても、その後に続きが来なければ、短い間隔の状態確認は空を引くだけになる。
- つまり、空かどうかで間隔を変えて得になるのは、「来た直後は、また来やすい」ときだけ。今の負荷と WP は生成が 60 秒続くのでそうなっていて、切断が無ければ T37 が速い。WB のまとまりは同じ 1 ms に 20 個で、1 回の答えで全部が見えるので、続きが無いと見ている。WR は 1 個ずつで、やはり続きが無いと見ている。到着がばらばらで前の到着から次が読めないなら、等間隔がいちばん待ちが短い。
- 切断があると T37 の得が消えるのは、この決まりが時間切れのときに間隔を変えないことと関わると見ているが、確かめていない。
- 学習の方針について: 「始まりや周期が分からない」だけでは、式を越える余地は出なかった（WP は W0 と同じ読み）。余地が出るのは、過去の到着から次の到着が読める負荷（生成が続く時間と止まる時間が入れ替わるもの）と、切断の扱いを合わせて決めるところだと見ている。

## 読むときの注意

- 替えた負荷の値は、確かめていない入力の上のなぞり直し。特に WB は 1 ms に 20 個を作る。今の負荷は 1 回に 4 個までで、20 個を一度に取るときの取得の動き（なぞり直しでは 8 個ずつ 2 ms で 3 回）は実測と照らしていない。
- WR は 1 本に 24 個しか無く、遅れの平均が荒い。
- WP は、周期の違う 3 つの形が seed ごとに混ざったもの。
- 「効く」には 3 マス中 2 マスが要り、2 マスは切断ありなので、切断の無いマスでだけ勝つ決まりは「効く」にならない。これは先に決めた読み方の性質。
- 最短が 2 秒より短い 4 通りは、ログに一度も現れていないソースの枝を通る（evidence/13 と同じ）。
- マスどうしは独立ではない（同じ 20 seed、同じ切断の時刻表）。
- 取り直しの単位は seed で、5 回の平均を seed の値にしている。5 回のあいだのばらつきは区間に入っていない。

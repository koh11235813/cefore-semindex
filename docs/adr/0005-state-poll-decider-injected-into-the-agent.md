# A state poll's interval may come from a decider injected into the agent

Stage 2 compares three ways of deciding a state poll's interval: a tuned language model, a policy learned from the logs and a fixed formula rule. The replay they were scored on asks a decider one question per decision, as an injected callable handed the decision's whole observable state. The agent had no such door: its interval came from whichever of several exclusive config fields was set, and none of them could be asked anything. The engine now takes a decider object at construction, named by one config field carrying a file's path, the digest of its bytes, a factory in that file and the factory's arguments, so the file scored in the replay is the file the emulator loads. The decider rides on the existing choices-plus-re-decision mode and replaces the uniform draw there, nothing else; a row's logged action probability is then 1 and no longer one over the number of choices. None of its code lives in this package, so the agent gains no dependency and a Mininet host imports numpy, or a socket client to a model server, only in a run that asked for one.

A decider is handed the whole decision state the row logs and, in addition, a bounded history of its pair's last eight resolved polls, which the engine did not keep before and which only a decider reads. ADR 0004 restricts its own policies to the newest poll's status and the count of consecutive timeouts, and already records that a later interval rule went outside that restriction. A decider goes further again, so the stepwise model of ADR 0004 does not cover it: the effect of this seam cannot be read from that model at all, only from runs.

A decider cannot be waited on inside the agent loop. The loop is one thread, so a node's sends, its replies to neighbors and its record creation all wait while a decision is being made, and a synchronous call of tens of milliseconds there is the same defect ADR 0004's Consequences record as measured and removed once. A decider may therefore answer later: it returns nothing at a resolution, the interval the pair already holds keeps the next poll armed, and the answer is applied when the decider yields it, against that poll's own send time and jitter draw, so an answer arriving before the instant it schedules produces the send instant a zero-latency answer would. One arriving after that instant but before the pair's next poll goes out sends the poll at once, later than a zero-latency answer would have, and is counted as clamped by the wait. The count leaves out an answer whose instant was already past when its poll resolved; the bound on the smallest choice below keeps that case out of a run whose loop is not stalled. What the wait changes is counted per node and written to the run's own log, together with the neighbor, the poll and the instant asked of every resolution still pending when the node stops. The run's behaviour is not changed to wait for them: shutdown collects once and does not wait, because an answer applied after the stop would move no poll.

## Considered Options

- **An exclusive config mode of the decider's own.** Rejected: it would duplicate the resolution gates the re-decision path already provides, and the fixed arms this comparison is read against would stop sharing that mode's jitter arithmetic, so a constant decider would no longer reproduce a single-choice run exactly.
- **The decider's code inside this package.** Rejected: it would put numpy, and for one candidate a socket client to a model server, into every Mininet host's import path, and the replay would no longer score the file the emulator runs.
- **A synchronous call to a model service, with a timeout and a fallback interval.** Rejected: it blocks the same loop, and a fallback that fires silently replaces the decider on the very rows the comparison is read from.
- **Pre-expanding the decider into a table keyed on the logged state.** Not available: these candidates read a feature vector, or its rendered text, together with the eight-row history, and almost every input they see is distinct. Only the scalar state an ADR 0004 policy reads is enumerable, and that is not what a decider reads.
- **Waiting at shutdown for the answers still outstanding.** Rejected: no poll of the run is left for such an answer to move, so waiting would delay the final counters line only to tidy a count. The instant each pending resolution was asked is recorded instead, which separates one asked less than the decider's own latency before the stop from one the decider was slow or absent on.

## Consequences

- A config field that names a file by path and runs it is code execution by configuration. It is acceptable here because the account that can write a node's config already runs the testbed as root through Mininet; the digest says which file ran, it does not make the mechanism safe elsewhere.
- The engine keeps a bounded per-pair history of resolved polls, in decider mode only, and appends to it outside the decision-logging gate, because the history is an input to the next decision and logging must not change behaviour. On the deferred path a row is appended when the answer arrives, so a decision asked while an answer is outstanding sees a history shorter by that row, and a decision whose answer never arrives is in no history at all. Neither has a count of its own: the first is implied by a late, overlapping or unanswered resolution, the second by an unanswered one. A late answer's row enters the history with the interval the decider chose, although the pair ran the held one.
- One protocol shape is admitted: a decider either always defers at a resolution or never does. The engine does not enforce it, and a pair's second deferral while its first answer is still outstanding is counted as an overlap rather than refused, because that is what any slow decider produces. Such a pair's answers must then come back in the order their resolutions happened, and one that does not stops the node, for the reason given with the row's stamps below. It is also why a pending request is keyed by its own poll and not by the pair: each answer is then applied with the send time and jitter draw of the poll it answers. Returning nothing at a send is not a deferral and is refused like any other invalid send-time answer.
- An answer whose interval is not one of the configured choices raises, and that value is checked before the answer's token is looked up, so such a decider fails loudly whichever answer it happens on. An in-choices answer matching no pending request is counted and dropped.
- A reschedule row's `ts_ms` is the resolution's own instant, so a deferred answer's row is stamped before the instant it was written, and that row carries besides when the answer was decided, whether it came too late to move the poll, and, when it did, the interval held instead. `clamped` still compares the armed instant against that same resolution instant, so it stays the field the replay and the other stages carry. Within one ordered pair those stamps must not go backwards, and the emit site raises rather than write one that does, because out-of-order rows make a negative age in every later reading.
- A decider's smallest choice, after jitter, must stay above the Interest lifetime plus the receive timeout, and the config refuses a run where it does not: below that bound a pair's next poll goes out before the previous one resolves, and the two state fields describing the newest poll stop meaning what the replay's fields of those names mean.
- The deferred path is a different decision rule in a countable set of cases, so a run is read as the decider's only together with its counts of deferred, applied, late, clamped-by-the-wait, overlapping, orphaned and unanswered resolutions.

# Agents open index.db with synchronous=NORMAL by default

Each Sync agent commits every received Index record in its own transaction on a WAL SQLite database. Under SQLite's default `synchronous=FULL` every commit costs an fsync, and with five agents on one virtual disk the fetching agent spent 33–89 ms handling each received record; that handling time, not the link or Cefore (a lone fetch returns in 1–2 ms), shaped fetch delays and the waits behind the per-neighbor in-flight cap (`docs/wayfinder/semindex-stage2/evidence/05/` section 4). With `synchronous=NORMAL` the same handling took 0 ms median and at most 1 ms (p99 1 ms) over 15 runs, fetch receive waits fell to 2–9 ms, link-up fetch timeouts at cap 32 (k = 4, p = 0.4) fell from 93 in an earlier FULL trial to 0, and discovery medians dropped (e.g. 6.08 s → 2.32 s at k = 8, p = 0) (`evidence/06/`). On real nodes, each with its own disk, an fsync is much cheaper than on this shared virtual disk, but under FULL a node still cannot take in records faster than it can fsync. We therefore made NORMAL the agents' default: we trade per-record durability for throughput, because the sync protocol re-fetches a lost record from any neighbor that still holds it, so an fsync per record buys little. The Store always issues the PRAGMA; there is no "leave SQLite's default" state.

## Considered Options

- **Keep FULL as the default and pass NORMAL in experiments**: rejected because FULL's per-record guarantee is one the protocol does not need, while it ties every node's receive rate to its fsync rate on any hardware; a default should describe the design we intend to deploy, and leaving it at FULL would also make every run depend on a flag whose absence silently changes the measured fetch timing.
- **Batch commits (commit every N records or every few ms) under FULL**: keeps one fsync per batch, but the records received since the last batch commit are lost even when only the agent process crashes, so it gives up more than NORMAL does (nothing is lost on an agent-process crash under WAL + NORMAL) and adds an open-transaction state to the receive path; not worth it while NORMAL already brings handling to ≤ 1 ms.
- **Put the database on tmpfs in experiments only**: would remove the fsync cost on the testbed but measure a storage setup no deployment has, and still leave FULL as the default the code describes.
- **Replace SQLite with another database or a custom store**: not needed now, since per-record handling is ≤ 1 ms under NORMAL. Revisit if the tail of per-record handling grows at larger scale or WAL checkpoint stalls appear; even then, the single-threaded design that handles one Data per loop step would likely limit throughput before the database does.

## Consequences

- An OS crash (not an agent-process crash, which loses nothing under WAL + NORMAL) may lose a node's own just-created records that no neighbor has fetched yet; lost records it had received are fetched again from any neighbor that still holds them.
- Runs recorded before this change ran with FULL; reproducing them needs `--store-synchronous FULL`. Their `meta.json` has `store_synchronous` null or missing, which aggregation keeps as an empty cell.
- `semindex.evalrun` always records the effective mode in `meta.json` (the given one, or NORMAL), never null. Generated agent configs still omit the key when no mode is given, so generated files are unchanged; only what they mean at run time changed.

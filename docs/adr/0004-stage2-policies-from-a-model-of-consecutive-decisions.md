# Stage 2 picks poll-interval policies on a model of consecutive decisions

Stage 2 collected, on a line of five nodes, a mixed stage A (each state-poll decision draws one of four intervals, 0.5 / 1.359 / 3.695 / 10.043 s, with probability 0.25) and fixed-arm stages B (every node always uses one interval), so that a learning method could be judged by whether A's data predicts what "every node always uses x" does in B. After the per-record fsync was removed (ADR 0003), A's per-decision values predict B within ±3% at p = 0, but at p > 0 a reward attached to each decision does not transfer from A to B: under the original rule (a record-hop's whole wait goes to the decision whose gap holds its arrival) the 4-hop error for the short arms is +26 to +92%, and re-charging each millisecond to the decision whose gap holds it is no better (+35 to +117%). The remaining error sits entirely in the time after the next poll, which the following decisions' intervals decide. A composition over consecutive decisions, built only from A's per-arm pieces (in-gap wait, the chance that a poll yields nothing, the chance that the next poll fails too, the gap after a failure, reply time), overlaps B within its standard error wherever the data identify it (`chain_step`: 1.359 s and 3.695 s at every p, 10.043 s at p ≤ 0.2) (`docs/wayfinder/semindex-stage2/evidence/07/` section 4). We therefore learn by building that model per (node, upstream) and choosing among state-dependent policies on it, rather than by learning per-decision values or values of whole decision sequences directly.

Policies may only look at what each decision already logs: the newest poll's status (`last_poll_status`: answered, pending, timed_out) and the number of polls since the last answered one that have passed their 2 s lifetime unanswered (`consecutive_poll_timeouts`, bucketed 0 / 1 / 2 / 3+). Inside the model, the chance that a failure continues is looked up by the time since the first unanswered poll, because in A the same failure count sits at different depths of an outage depending on the earlier, random arms. Under a policy indexed by the count, the policy's own arms fix that time (up to the ±10% jitter and about 50–60 ms of loop time), so the count-to-time conversion is the only link between the policy table and the model.

The model reports, for each candidate policy, the mean 4-hop latency and the control bytes per record. Dominated policies are dropped, the remaining frontier is compared with the stage-1 default (C, 2 s ± 20%), and one or two policies from it are then run as a validation stage. No latency/bytes weight is fixed beforehand, because the size of the gain is unknown until the frontier exists. At 20 seeds per p, a stage-to-stage difference of about 1–1.5% in control bytes per record is distinguishable (run-to-run SD 0.7–2.3%), while 4-hop latency needs roughly 9–23% (its standard error is 3–8%).

## Considered Options

- **A per-decision contextual bandit** (state buckets, one reward per decision): rejected, because the reward does not transfer from A to B at p > 0 under either attribution rule tried; a bandit learned on A would rank the short arms on costs that the next decisions, not the chosen arm, produced.
- **Model-free sequential learning** (values of state and arm learned from A's logged sequences by bootstrapping, or on-policy runs): kept as the next step if the model's predictions fail validation. Not chosen first because its assumptions about the state end up inside the learned values, where they can only be checked end-to-end by running the policy, while the model's pieces can be checked one by one against B (`evidence/07/seq_pieces.csv`); for the 0.5 s arm a 10 s outage spans about 20 consecutive decisions, over which bootstrapping errors accumulate.
- **Off-policy evaluation by importance sampling over all-x spans**: unusable for the short arms at p > 0 (−27 to −80%), since A almost never holds the long runs of identical short arms an outage needs.
- **Let policies see the time since the first unanswered poll**: closer to the outage process, but needs new agent state and log fields; the count already determines that time under a fixed policy. Neither form can see when the link actually went down, which can precede the first unanswered poll by up to one interval.

## Consequences

- The need to model consecutive decisions comes from how this testbed fails links: evalgen takes each link down for whole 5 s slots, so the chance that a failure continues depends on the interval (at p = 0.2, 0.91 / 0.77 / 0.39 / 0.15 for 0.5 / 1.359 / 3.695 / 10.043 s, while a single poll fails with the same 0.19–0.20 for every arm). Policies chosen here are tuned to 5 s slot outages. We keep that outage model through the first validation and decide on other outage shapes after it.
- h2's scheduled probe fetched its content body synchronously inside the agent loop, so `on_tick` stopped meanwhile and 3.9–8.8% of h2's polls (0.1% in the 10.043 s B stage, whose polls apparently stay out of phase with the 10 s probes; not verified) went out 1.0–1.2 s late, unevenly across arms (`evidence/07/` section 5). The probe body fetch becomes a chunk-by-chunk state machine driven by the same loop (one cefpyco handle and one thread, since cefpyco keeps its handle, receive buffer and parse position in process-wide statics; one fetch in flight at a time), which keeps the application's body traffic on the links.
- The model is fitted to data collected after that change: A, B and C are run again (1000 runs, about 44 h), so that training data and baselines share one code version. The existing NORMAL runs (`s4*`) are used only to build and test the model code meanwhile.
